# Migration engine

| | |
|---|---|
| Status | Baseline (Wave 0), awaiting owner approval |
| Applies to | Wave 6 (core), Wave 10 (REOSA import) |
| Read before | [`../00-product/constitution.md`](../00-product/constitution.md) Part III |

The migration engine is a core feature of ExponetDB, not a side system. Today an
AI agent can apply SQL to REOSA's production database through a hosted
provider's MCP with one broad credential; the safety of that path rests on the
agent following written rules. ExponetDB keeps the convenience and replaces the
written rules with an engine.

## The engine on one page

```
              author (human or agent)                                 ExponetDB
 ┌──────────────────────────────────────────┐        ┌────────────────────────────────────────────────────────┐
 │ 01JB…_add-lead-index/                    │        │ ingest: validate manifest, compute checksums, store     │
 │   migration.yaml  (ULID id, dependsOn,   │  plan  │ inspect target: identity, ledger, fingerprint, sizes    │
 │                    transactional, …)     │ ─────▶ │ order (DAG) · analyze (compat, locks, rewrite) · lint   │
 │   up.sql   verify.sql   [down.sql]       │        │ evidence (staging verified, same checksum & digest)     │
 └──────────────────────────────────────────┘        │ authorize (RBAC ∩ scope ∩ grant) · policy decision      │
                                                     │ → immutable plan pln_… (expires, single-use, bound)     │
                                                     └────────────────────────────────────────────────────────┘
                                         apply(pln_…)                          │
                                                     ┌────────────────────────▼───────────────────────────────┐
                                                     │ re-check bindings · lease · advisory lock · re-check    │
                                                     │ per migration: execute · pre-commit gate · ledger row   │
                                                     │ · COMMIT · verify (structural, verify.sql, engine)      │
                                                     │ mirror · unlock · audit                                  │
                                                     └─────────────────────────────────────────────────────────┘
```

|---|---|---|
| Identity | ULID, 26 characters, generated by the author; name is a label | [`migration-bundles.md`](./migration-bundles.md) |
| Content binding | Apply checksum over normalized executable text of `up.sql` + execution-relevant manifest fields; verify and rollback digests separate | [`migration-bundles.md` §3](./migration-bundles.md#3-checksum-semantics) |
| Order | DAG from `dependsOn`; ULID tie-breaker; never file names | [`dependency-graph.md`](./dependency-graph.md) |
| Analysis | compatibility class, lock severity, rewrites, dependents, lint; `unknown` is never `safe` | [`analysis.md`](./analysis.md) |
| Plan | immutable, short-lived, single-use; bound to actor, client, target generation, checksum, fingerprint, ledger hash, evidence, policy | [`planning-and-apply.md`](./planning-and-apply.md) |
| Concurrency | Control Store lease + session advisory lock in the target | [`concurrency.md`](./concurrency.md) |
| Verification | pre-commit gate, structural, reviewed `verify.sql` (conservative admission, defense in depth), engine checks, staging evidence; status separate from apply | [`verification.md`](./verification.md) |
| Ledger | inside each target (`exponetdb.schema_migrations`), mirrored in the Control Store; append-only | [`ledger.md`](./ledger.md) |
| Staging first | production requires same checksum + passed verification (same verify digest) on the evidence environment | [`staging-production-policy.md`](./staging-production-policy.md) |

| Failures | recovery is always a new planned operation | [`failure-and-recovery.md`](./failure-and-recovery.md) |
| Tooling | CLI, CI, source references, runtime schema contract | [`authoring-and-ci.md`](./authoring-and-ci.md) |

## Invariants (summary)

1. An applied migration id is bound to its apply checksum forever.
2. Order comes from the DAG.
3. Only the bytes stored in the plan are executed.
4. A stale plan is refused, never refreshed.
5. One schema change per target at a time.
6. Applied ≠ verified; both are recorded separately.
7. Nothing re-runs automatically; `down.sql` never runs automatically.
8. Production needs verified staging evidence for the identical checksum.
9. The ledger lives in the target and is mirrored; divergence blocks changes.
10. Legacy history is imported by evidence, not by name, and then frozen.

## What the engine does not do

- Generate migrations from a desired schema (no "diff and apply" mode). Drift
  detection can show differences; turning them into a migration is an authored
  bundle. A schema-diff-to-bundle assistant may come later as tooling, never as an
  automatic apply path.
- Run data backfills of unbounded size inside schema transactions.
- Manage cluster-level objects (roles, role settings, extensions, `pg_hba`,
  configuration). Those are node capabilities with their own plans
  ([`../07-node-agent/capabilities.md`](../07-node-agent/capabilities.md)),
  because they are cluster-wide: on a cluster that hosts staging and production,
  a role created "for staging" exists for production too.
- Depend on an ORM.
