A migration bundle is the unit of schema change in ExponetDB. It is a directory
in the consumer's repository, transported to ExponetDB as exact bytes, hashed,
planned, applied, verified and recorded.

## 1. Layout

**[DECIDED]**

```
<migrations-root>/
├── exponetdb.project.yaml                      # project configuration (§6)
├── 01JB2Z6G8M4Q7R9T1V3W5X7Y9Z_add-lead-index/
│   ├── migration.yaml                          # required
│   ├── up.sql                                  # required
│   ├── verify.sql                              # required by default lint profile, see §4
│   └── down.sql                                # optional
└── 01JB2ZA1KQ0D3H5J7M9P1R3T5V_backfill-lead-source/
    ├── migration.yaml
    ├── up.sql
    └── verify.sql
```

Rules:

- The directory name is `<id>_<name>`. `<id>` is a ULID; `<name>` is a
  kebab-case slug `[a-z0-9]+(-[a-z0-9]+)*`, at most 64 characters. A directory
  whose name does not match the manifest's `id` and `name` is
  `MIGRATION_BUNDLE_INVALID`.
- Only the four file names above are allowed in a bundle directory. Any other
  file is `MIGRATION_BUNDLE_INVALID` (no hidden includes, no `\i`, no helper
  scripts that would bypass hashing).
- All files are UTF-8. A UTF-8 byte order mark is rejected. NUL bytes are
  rejected. Line endings are normalized for hashing (§3) but the stored bytes
  are kept as received.
- Maximum sizes (V1): `up.sql` 4 MiB, `verify.sql` 512 KiB, `down.sql` 4 MiB,
  `migration.yaml` 64 KiB. A data migration that needs more belongs in a
  separate data-loading tool, not in a schema migration.

### Migration ids

**[DECIDED]** Ids are ULIDs: 26 characters of Crockford base32 encoding 48 bits
of millisecond timestamp and 80 bits of randomness, for example
`01JB2Z6G8M4Q7R9T1V3W5X7Y9Z`. They are generated by the author's tooling (the
ExponetDB CLI, or any ULID library), never assigned centrally.

**[OBSERVED]** The owner brief's example `01K6XQ4E9N8T3G5Y7Z2M` has 20
characters and is therefore not a valid ULID; it is read as an illustration of
the format. **[DECIDED]** ExponetDB validates the full 26-character form,
uppercase, Crockford alphabet (no `I`, `L`, `O`, `U`), first character `0` to
`7`.

Why ULIDs: several Claude Code sessions and developers create migrations in
parallel. **[OBSERVED]** REOSA's sequential numbering produced real collisions
(see [`../13-integrations/reosa-current-state.md`](../13-integrations/reosa-current-state.md#numbering-and-collisions)).
ULIDs need no coordination, sort roughly by creation time, and are readable in
file listings.

**[DECIDED]** The ULID timestamp **does not define execution order**. Order comes
from the dependency graph; the id only breaks ties deterministically
([`dependency-graph.md`](./dependency-graph.md)). Clock skew between authors'
machines is therefore harmless.

## 2. Manifest `migration.yaml`

**[DECIDED]** Schema identifier `exponetdb.migration/v1`. The JSON Schema is
generated from `packages/contracts` and published with the CLI. Unknown keys are
an error (strict), so that a typo such as `transactinal: false` cannot silently
fall back to a default.

```yaml
schema: exponetdb.migration/v1          # required, exact string
id: 01JB2Z6G8M4Q7R9T1V3W5X7Y9Z          # required, ULID, must match directory
name: add-lead-index                    # required, slug, must match directory
description: |                          # required, 1..2000 chars, plain text
  Adds a partial index on leads(tenant_id, created_at) for the inbox query.

dependsOn:                              # required (may be empty list)
  - 01JB2YX7M3K5N7Q9S1V3W5Y7A9          # ULIDs in the same project stream
  - baseline:reosa-platform-2026-11     # or a baseline node, see dependency-graph.md

execution:
  transactional: true                   # required, see §5
  lockTimeout: 5s                       # optional, default from project config
  statementTimeout: 10m                 # optional, default from project config
  role: owner                           # optional, execution role alias from project config
  searchPath: ["public"]                # optional, default from project config; pinned for execution

requires:                               # optional
  postgres: ">=16 <19"                  # semver-like range over server major.minor
  extensions:
    - name: vector
      version: ">=0.7.0"
    - name: pg_trgm

compatibility:
  declared: additive                    # required: additive | potentially_breaking | data_rewrite | destructive
  notes: |                              # required unless declared = additive
    …

verification:
  expectations: auto                    # auto | none; see verification.md
  runtimeChecks: verify.sql             # verify.sql | none

rollback:
  script: down.sql                      # down.sql | none
  safety: unsafe                        # safe | lossy | unsafe ; required if script present
  notes: |
    Drops the index. Safe; no data loss.

source:                                 # optional, informative authoring metadata
  authors: ["dev@example.com"]          # never hashed, may be redacted in audit
  ticket: "LIN-1234"
```

The manifest's `source` block holds only authoring metadata (`authors`,
`ticket`). The repository reference (repository, commit, path, provenance) is
not part of the manifest, because a file cannot name the commit that contains
it; it is submitted with the bundle
([`authoring-and-ci.md` §1](./authoring-and-ci.md#1-source-reference-model)).
**[DECIDED]** (Wave 1 clarification.)

Field reference:

| Field | Required | Hashed into apply checksum | Meaning |
|---|---|---|---|
| `schema` | yes | yes | Manifest format version. |
| `id` | yes | yes | Migration identity. |
| `name` | yes | no | Human label; renaming a bundle directory after application is a lint warning, not a mismatch. |
| `description` | yes | no | Why the change exists. Shown in plans and approvals. |
| `dependsOn` | yes | yes | Graph edges. Changing them changes what the migration *means*. |
| `execution.transactional` | yes | yes | Executor mode. |
| `execution.lockTimeout`, `statementTimeout` | no | yes | They change runtime behavior. |
| `execution.role` | no | yes | Which role executes. |
| `execution.searchPath` | no | yes | Unqualified names resolve differently under another `search_path`. |
| `requires.*` | no | yes | Preconditions are part of the contract. |
| `compatibility.declared`, `notes` | yes | `declared`: yes; `notes`: no | Declared class gates policy; changing it after staging must invalidate evidence. |
| `verification.expectations`, `runtimeChecks` | yes | no (see verify digest) | Verification is versioned separately (§3). |
| `rollback.*` | no | no (see rollback digest) | Rollback is versioned separately (§3). |
| `source.*` | no | no | Informational. |

Durations use the Go/Prometheus style `5s`, `10m`, `1h` (no ISO 8601 here,
because it is the most common notation in PostgreSQL tooling and readable in
YAML). Maximums: `lockTimeout` 60 s (higher needs acknowledging the
`long_lock_timeout` lint), `statementTimeout` 6 h.

**[DECIDED]** (Wave 1 clarification; the manifest schema in
`packages/contracts` enforces it):

- Duration grammar: one to four components in the fixed order hours, minutes,
  seconds, milliseconds, each a decimal integer without leading zeros followed
  by its unit: `^(N h)?(N m)?(N s)?(N ms)?$` with `N = 0|[1-9][0-9]{0,8}` and no
  spaces (`1h30m`, `90s`, `250ms`). At least one component; no fractions, no
  signs, no other units.
- Both timeouts must lie in 1 ms to 6 h. Zero is refused because PostgreSQL
  reads `0` as "no timeout". The schema accepts a `lockTimeout` above 60 s; the
  `long_lock_timeout` lint (Wave 6) asks for the acknowledgement.
- `name` is at most 64 characters; `description` has 1 to 2000 Unicode code
  points; `compatibility.notes` is required and non-empty unless `declared` is
  `additive`.
- `rollback.safety` is required when `rollback.script` is `down.sql` and must be
  absent when it is `none`.
- `execution.role` is an alias (`^[a-z][a-z0-9_]{0,62}$`) that the project
  configuration maps to a PostgreSQL role; `execution.searchPath` entries are
  schema names of 1 to 63 bytes without control characters, order significant.
- `requires.postgres` and `requires.extensions[].version` are space-separated
  comparators `(>=|<=|>|<|=)?<version>` with dotted numeric versions;
  extension names (`^[a-z0-9][a-z0-9_-]{0,62}$`) are unique within the list.
- `dependsOn` entries are migration ULIDs or `baseline:<slug>`, where `<slug>`
  follows the bundle-name rule `[a-z0-9]+(-[a-z0-9]+)*` with at most 64
  characters (the same rule everywhere a baseline id appears, including the
  ledger and `ls1`); duplicates are allowed in the file and removed in the
  canonical form (lint `duplicate_dependency`, info).
- `migration.yaml` is a single YAML 1.2 document under the core schema, with
  unique keys, no anchors or aliases, and no tags.

A bundle is also invalid (`MIGRATION_BUNDLE_INVALID`) when `verify.sql` exists
but `verification.runtimeChecks` is `none` (or the reverse), or when `down.sql`
exists but `rollback.script` is not `down.sql` (or the reverse). Nothing in a
bundle may be present without a manifest field that says what it is for.

**[DECIDED] Manifest versioning.** A future `exponetdb.migration/v2` is accepted
only by engines that declare support for it. The engine supports reading every
version it ever supported (applied history must stay readable). A bundle never
changes its manifest version after application, because the schema version is
hashed.

## 3. Checksum semantics

**[DECIDED]** ([ADR-0009](../01-architecture/adr/0009-checksum-semantics.md))
ExponetDB computes three digests per bundle and one derived identifier:

| Digest | Input | Purpose | May change after apply? |
|---|---|---|---|
| **apply checksum** (`checksum`) | manifest execution fields + `up.sql` | **Identity binding of the migration id.** Recorded in the ledger. Compared on every plan. | **Never.** Change = `MIGRATION_CHECKSUM_MISMATCH`. |
| **verify digest** | the complete normalized `verify.sql` source, comments included (+ `verification.*` fields) | Binds the whole verification contract: the checks and their directives (`-- check:`, `-- covers:`, `-- calls:`, `-- reads-view:`). Records which verification ran. | Yes, through an explicit verification revision (see [`verification.md`](./verification.md#retrying-verification)). |
| **rollback digest** | `down.sql` (+ `rollback.*` fields) | Records which rollback script was reviewed. | Yes; a rollback plan binds the digest it will execute. |
| **bundle digest** | the three digests above | Content id for storage and evidence matching. | Derived. |

Why split: an applied migration's identity must be immutable, but a bug in a
verification query or an improvement to a rollback script must be fixable
without pretending the migration itself changed. Staging evidence binds the apply
checksum **and** the verify digest
([`staging-production-policy.md`](./staging-production-policy.md)), so changing
`verify.sql` between staging and production forces re-verification on staging,
not a silent pass.

### Canonical serialization (version `c1`)

**[DECIDED]**

1. **SQL text normalization.** The apply checksum (`up.sql`) and the rollback
   digest (`down.sql`) bind the **executable text**, not the bytes, because
   comments there are documentation. The verify digest is different: it binds
   the complete `verify.sql` source after the input checks and line-ending
   normalization only, because comments in `verify.sql` carry verification
   semantics (item 4 and the normative definition below). **[OBSERVED]** REOSA edits comment headers of migrations after
   they were applied (for example renumbering notes in `0370`, `0371`, `0373`,
   and the comment-only fix in commit `58de20b4`); a byte hash would turn every
   such edit into a false `MIGRATION_CHECKSUM_MISMATCH`, and false alarms train
   people to bypass the check. The normalization is purely lexical (it never
   parses or re-prints SQL, so it cannot drift with a parser version):
   - input must be valid UTF-8, no BOM, no NUL;
   - convert `\r\n` and lone `\r` to `\n`;
   - tokenize with PostgreSQL's lexical rules under
     `standard_conforming_strings = on` (the engine pins this setting during
     execution, see [`planning-and-apply.md`](./planning-and-apply.md#5-session-settings)):
     single-quoted strings, `E''` strings, `U&''` strings, dollar-quoted strings
     (any tag), quoted identifiers, nested `/* */` comments, `--` comments;
   - **remove** comments that are *outside* literals and quoted identifiers;
     comments inside a dollar-quoted body (for example inside a function body)
     are literal content and are **kept**, because they end up in `pg_proc.prosrc`;
   - **collapse** every run of whitespace outside literals and quoted identifiers
     to one space, and trim both ends;
   - keep everything else byte-for-byte (no case folding, no keyword
     normalization).

   The engine additionally records a **source digest** (SHA-256 of the
   line-ending-normalized raw bytes). A changed source digest with an unchanged
   apply checksum is reported as lint `comment_only_change` (info), never as an
   error. Golden vectors include adversarial cases (`--` inside strings,
   `$$` inside `E''` strings, nested comments, unterminated literals which are
   rejected) so that no two executable texts can normalize to the same string.
   Consumers are told to add `*.sql text eol=lf` to `.gitattributes`.
2. **Manifest field selection**: the hashed fields listed in §2 are extracted
   from the parsed YAML into a JSON object with exactly these keys:
   `schema, id, dependsOn, execution{transactional, lockTimeout, statementTimeout, role, searchPath}, requires{postgres, extensions[]}, compatibility{declared}`.
   Defaults are **materialized** (an omitted `lockTimeout` becomes the project
   default *at bundle-ingest time*, recorded in the stored manifest), so that a
   later change of the project default cannot change what an applied migration
   meant. `dependsOn` is sorted lexicographically; `requires.extensions` sorted by
   `name`. Durations are normalized to integer milliseconds. The exact
   projection, including the materialization order, is in the normative
   definition below.
3. **JSON canonicalization**: RFC 8785 (JCS).
4. **Framing**: the hash input is a sequence of length-prefixed fields so that
   no concatenation ambiguity exists:

   ```
   apply_input =
       "exponetdb/migration-checksum/c1\n"
     + frame("manifest", JCS(manifest_exec_fields))
     + frame("up.sql",   executable_text(up.sql))
   frame(label, bytes) = label + "\n" + decimal(len(bytes)) + "\n" + bytes + "\n"
   checksum = "sha256:c1:" + hex(SHA-256(apply_input))
   ```

   The verify and rollback digests use the same construction with prefixes
   `exponetdb/verify-digest/c1` and `exponetdb/rollback-digest/c1`, and an
   absent file framed as `frame("verify.sql", "")` with a separate `absent`
   marker label (`frame("verify.sql:absent","")`) so that "empty file" and "no
   file" differ. The rollback digest frames the executable text of `down.sql`;
   the verify digest frames the normalized source of `verify.sql`, comments
   included. The normative definition below states the byte sequence exactly
   (an absent file is both frames, in this order).

5. **Versioning**: the `c1` tag is part of the stored value. A future
   canonicalization `c2` never re-hashes history; ledger rows keep their `c1`
   value, and comparisons are always made with the canonicalizer named in the
   stored value.

### Normative definition of `c1` (frozen at G1)

**[DECIDED]** (Wave 1 clarification of the rules above, made before any `c1`
value was stored.) This is the exact algorithm that the production code in
`packages/migrations/format` and the Go conformance implementation in
`agent/node/internal/conformance` implement independently. Golden vectors in
`tooling/golden/` pin it. Where this section and the summary above seem to
differ, this section is the specification.

**Freeze.** Until the owner accepts G1, `c1` may still be corrected under the
name `c1` (no value has been stored anywhere); every correction updates this
section, the golden vectors and both implementations together and is listed
in the [G1 gate record](../14-roadmap/gates/1.md). From the owner's acceptance
of G1 on, the output of `c1` for any input never changes, locked golden
vectors are append-only, and any change of behavior is a new canonicalizer
`c2` introduced by an ADR.

**N1. Input checks**, in this order; the first failure is the result:

1. The bytes are well-formed UTF-8 (no overlong forms, no surrogate code points,
   nothing above U+10FFFF): otherwise `invalid_utf8`.
2. The text does not start with U+FEFF: otherwise `bom`. U+FEFF elsewhere is an
   ordinary character.
3. The text contains no U+0000: otherwise `nul`.

**N2. Line endings.** Every CR LF pair becomes LF, then every remaining CR
becomes LF, everywhere (also inside literals). The text has no CR afterwards.

**N3. Character classes** (code points):

| Class | Members |
|---|---|
| whitespace | U+0020, U+0009, U+000A, U+000B, U+000C |
| ident_start | `A`–`Z`, `a`–`z`, `_`, every code point ≥ U+0080 |
| ident_cont | ident_start, `0`–`9`, `$` |
| tag_start / tag_cont | ident_start / ident_start and `0`–`9` |

These are the classes of PostgreSQL's lexer (`scan.l`) in PostgreSQL 17 and
18. PostgreSQL 16 does not count U+000B as whitespace; SQL that uses it outside
literals fails to parse on PostgreSQL 16 and cannot be applied there.

**N4. Scan.** From the first code point, the first matching rule applies:

| # | At the current position | Token |
|---|---|---|
| R1 | `--` | line comment, up to but excluding the next LF, or to the end |
| R2 | `/*` | block comment. Inside, from left to right: `/*` raises the depth, `*/` lowers it, anything else is skipped one code point at a time (`/*` is tested before `*/`). The comment ends when the depth returns to zero. End of input inside: `unterminated_block_comment` |
| R3 | a whitespace code point | whitespace |
| R4 | `'` | string literal, standard mode |
| R5 | `e` or `E` followed by `'` | string literal, escape mode (the prefix belongs to the token) |
| R6 | `u` or `U` followed by `&'` | string literal, standard mode (prefix included) |
| R7 | `u` or `U` followed by `&"` | quoted identifier (prefix included) |
| R8 | `"` | quoted identifier |
| R9 | `$`, an optional tag (tag_start tag_cont*), `$` | dollar-quoted literal with that tag |
| R10 | an ident_start code point | identifier run: that code point and the longest following run of ident_cont |
| R11 | any other code point (including a `$` that does not open R9) | ordinary code point |

String literal: after the opening quote, `''` is content; in escape mode `\`
and the code point after it are content; a single `'` closes. After the closing
quote, if the following text is a run of whitespace code points and line
comments (as in R1) that contains at least one LF and is immediately followed by
`'`, the literal **continues** in the same mode after that `'`, and the run and
both quotes belong to the token (PostgreSQL's string continuation). End of input
inside: `unterminated_string`.

Quoted identifier: `""` is content, a single `"` closes; no continuation. End of
input inside: `unterminated_quoted_identifier`.

Dollar-quoted literal: the content runs up to the first following occurrence of
the exact opening delimiter `$tag$` (tags are case-sensitive). End of input
inside: `unterminated_dollar_quote`.

**N5. Output (executable text).** Tokens from R4 to R11 are copied unchanged,
including prefixes, quotes and continuation text. Each maximal run of
whitespace and comments between tokens becomes exactly one U+0020; a run at the
start or at the end of the text is removed. The result, encoded as UTF-8, is
the executable text; it may be empty. A comment therefore separates tokens like
a space: `foo/**/bar` becomes `foo bar`, and `-/**/-` becomes `- -`, never
`--`. No case folding, no Unicode normalization, no keyword handling.

The scan follows PostgreSQL's lexer wherever it decides where comments,
literals and quoted identifiers begin and end. It differs only on text that
PostgreSQL rejects as a lexical error (for example a numeric literal followed
directly by identifier characters, such as `1e'x'`), which cannot be applied.

**N6. Frames and digests.** `frame(label, b) = UTF8(label) LF decimal(len(b)) LF
b LF`, where `len` counts bytes and `decimal` has no leading zeros (`0` for an
empty `b`). `S(f)` is the normalized source of file `f`: its text after N1 and
N2, encoded as UTF-8, with every comment and all whitespace kept. `X(f)` is the
executable text of file `f` (N3 to N5, applied to `S(f)`). All digests use
SHA-256 and lowercase hexadecimal.

| Value | Hash input | Format |
|---|---|---|
| apply checksum | `"exponetdb/migration-checksum/c1" LF` + `frame("manifest", JCS(P))` + `frame("up.sql", X(up.sql))` | `sha256:c1:<hex>` |
| verify digest | `"exponetdb/verify-digest/c1" LF` + `frame("manifest", JCS(V))` + `F("verify.sql", S)` | `sha256:c1:<hex>` |
| rollback digest | `"exponetdb/rollback-digest/c1" LF` + `frame("manifest", JCS(R))` + `F("down.sql", X)` | `sha256:c1:<hex>` |
| bundle digest | `"exponetdb/bundle-digest/c1" LF` + `frame("checksum", c)` + `frame("verifyDigest", v)` + `frame("rollbackDigest", r)`, with the three values above as ASCII | `sha256:c1:<hex>` |
| source digest | `S(up.sql)` | `sha256:<hex>` |

`F(name, T)` is `frame(name, T(file))` when the file is present, and
`frame(name, "")` followed by `frame(name + ":absent", "")` when it is absent.

The source digest and the verify digest both start from the normalized source
`S`, but they are different contracts. The source digest is an unprefixed
`sha256:` over `S(up.sql)` alone: an informational record of the exact
`up.sql` text that only feeds the `comment_only_change` lint and never decides
identity. The verify digest is a `c1` value over the framed verify projection
and `S(verify.sql)`: it decides whether production evidence matches.
`verify.sql` is also scanned (N4); a lexically broken file is refused with
the N4 codes, but `X(verify.sql)` is not hashed.

**N7. Projections.** JCS is RFC 8785. Every key below is always present; `null`
stands for "not set".

- `P` (apply): `{"schema", "id", "dependsOn", "execution": {"transactional",
  "lockTimeout", "statementTimeout", "role", "searchPath"}, "requires":
  {"postgres", "extensions"}, "compatibility": {"declared"}}`.
  `dependsOn`: the entries without duplicates, sorted by code point.
  `lockTimeout`, `statementTimeout`: integer milliseconds, materialized from the
  manifest, else the project configuration's `defaults`, else the engine
  defaults 5 s and 15 min
  ([`planning-and-apply.md` §5](./planning-and-apply.md#5-session-settings)).
  `role` and `searchPath`: materialized from the manifest, else the project
  configuration's `defaults.role` and `defaults.searchPath`; there is no engine
  default, and a bundle where either stays unresolved is
  `MIGRATION_MANIFEST_INVALID` (fail closed, C-11). `searchPath` keeps its
  order. `requires.postgres`: the string as written, or `null`.
  `requires.extensions`: `[{"name", "version"}]` sorted by `name`, `version` as
  written or `null`; `[]` when absent.
- `V` (verify): `{"verification": {"expectations", "runtimeChecks"}}`.
- `R` (rollback): `{"rollback": null}` when the manifest has no `rollback`
  block, else `{"rollback": {"script", "safety", "notes"}}` with `safety` and
  `notes` as written or `null`.

The project defaults are checked with the same rules as the manifest fields
whether or not a default is used. Errors are reported in this order: project
defaults, the projections `P`, `V`, `R`, then the files `up.sql`, `verify.sql`,
`down.sql` (the first failure is the result). Timeout errors are
`invalid_duration` (grammar) and `duration_out_of_range` (bounds); unresolved
materialization is `unresolved_execution_role` or `unresolved_search_path`.

The digest layer does not check that the files agree with the manifest
(`runtimeChecks`, `rollback.script`); bundle validation does, before anything is
stored, so a stored bundle never has a framed absence that contradicts its
manifest.

**[DECIDED]** (pre-G1 correction, 2026-10-05) **The verify digest binds the
full normalized `verify.sql` source.** Comments in `verify.sql` are not
documentation: `-- check:` names a check, `-- covers:` declares which
statements a check verifies, and `-- calls:` and `-- reads-view:` declare
consumer code that changes admission and requires approval
([`verification.md` §4](./verification.md#4-runtime-verification-verifysql)).
A digest over the executable text would let these directives change while the
verify digest, and therefore the production evidence that matches on it
([`staging-production-policy.md`](./staging-production-policy.md)), stays the
same. Binding the whole source is deliberately conservative:

- every comment and whitespace edit changes the verify digest, which costs at
  most a re-verification on the evidence environment;
- a directive added in a later wave is bound from its first use, without a
  change of this specification or a parser that tells "semantic" from other
  comments;
- only line endings are normalized (N2), so a CRLF checkout matches an LF one;
- the apply checksum does not depend on `verify.sql` at all, so a
  verify-only edit never changes the migration's identity, and the rollback
  digest keeps framing `X(down.sql)` (`down.sql` has no directives).

The golden vectors `c1-bundle-014`, `054` and `100` to `115` pin these
properties ([gate record](../14-roadmap/gates/1.md)).

**[DECIDED]** The checksum function lives in the pure part of
`packages/migrations` (`format/` subpath: no I/O, no database; imports only
`kernel` and the manifest schema from `contracts`), shared byte-for-byte by the
server, the CLI and the Control Store runner. It is built in Wave 1 as
production code and frozen when the owner accepts the Wave 1 gate (G1): from
then on its output never changes, and a change is a new canonicalizer `c2`
([`../01-architecture/package-architecture.md` §1.1](../01-architecture/package-architecture.md#11-packagesmigrations-by-subpath-and-wave)).
A golden-vector test suite (bundles and expected digests, append-only) is
committed and must pass for every implementation: the TypeScript production
code and the independent Go conformance implementation.

### What a mismatch means

| Situation | Result |
|---|---|
| Same id, same apply checksum, already in target ledger | `MIGRATION_ALREADY_APPLIED` (not an error for status queries; a no-op for plans that include it) |
| Same id, different apply checksum than the ledger of **any** target of the project | `MIGRATION_CHECKSUM_MISMATCH`, plan denied, rule not overridable |
| Same id, different apply checksum than a previously ingested bundle never applied anywhere | Allowed (the earlier content was never history), but the lint reports `rewritten_unapplied_migration` and the old content stays in the bundle store for audit |
| Same apply checksum, different verify digest than the staging verification | Production plan requires re-verification on staging (`migration.staging-verify-digest`) |
| Legacy-imported migration file edited later | `MIGRATION_CHECKSUM_MISMATCH` against the import checksum, see [`legacy-import.md`](./legacy-import.md) |

## 4. `up.sql`, `verify.sql`, `down.sql`

### `up.sql`

Plain SQL, executed statement by statement after parsing (never as one
multi-statement string, see [`planning-and-apply.md`](./planning-and-apply.md#7-statement-execution)).

**Forbidden** in every `up.sql` (`MIGRATION_STATEMENT_FORBIDDEN`):

- transaction control: `BEGIN`, `START TRANSACTION`, `COMMIT`, `ROLLBACK`,
  `SAVEPOINT`, `RELEASE`, `PREPARE TRANSACTION`, `COMMIT PREPARED`;
- session-level settings that would leak: `SET` without `LOCAL` (except inside
  function definitions), `RESET ALL`, `SET ROLE`, `SET SESSION AUTHORIZATION`,
  `DISCARD`;
- psql meta-commands (`\i`, `\set`, `\connect` …): rejected by the parser;
- cluster-level and privileged statements that belong to node capabilities:
  `CREATE/ALTER/DROP ROLE|USER|GROUP`, `ALTER SYSTEM`, `CREATE/DROP DATABASE`,
  `CREATE/ALTER/DROP TABLESPACE`, `LOAD`, `CREATE EXTENSION` of an extension not
  listed as trusted for the project, `COPY ... TO/FROM PROGRAM`, `COPY ... FILE`;
- statements touching the `exponetdb` schema.

Extensions: a migration **declares** extension requirements in
`requires.extensions`; installing an extension is a separate privileged operation
(`postgres.extensions.apply`) because it often needs superuser
([C-21](../00-product/constitution.md#c-21-no-superuser-credentials-in-the-control-plane-for-agent-managed-clusters)).
Exception: a project may list *trusted* extensions (PostgreSQL's `trusted`
extensions that the execution role may create) in `exponetdb.project.yaml`;
`CREATE EXTENSION IF NOT EXISTS <trusted>` is then allowed in `up.sql`.

### `verify.sql`

Read-only checks executed after apply. They are part of the reviewed bundle:
their verify digest, which binds the whole file including its comment
directives, is bound into the plan and approval, and they can be fixed later
through a verify revision without re-applying `up.sql`. V1 admits only
`SELECT` checks with an `ok` column and allowlisted built-in functions; `DO`
blocks are not allowed. Trust model, admission, execution and examples:
[`verification.md`](./verification.md#4-runtime-verification-verifysql). Required by the default lint profile
(`missing_verify_sql` is a blocking lint for prod-tier projects; teams can
lower it per project, with the lowering recorded).

### `down.sql`

Optional. Never executed automatically. Its presence enables a `migration.rollback`
plan. See [`failure-and-recovery.md`](./failure-and-recovery.md#3-downsql).

## 5. Transactional and non-transactional bundles

**[DECIDED]**

- `transactional: true` (default and strongly preferred): all statements of
  `up.sql`, the ledger insert and the post-apply structural checks run in **one**
  transaction. Either everything commits or nothing does.
- `transactional: false`: required when `up.sql` contains statements PostgreSQL
  refuses inside a transaction block (for example `CREATE INDEX CONCURRENTLY`,
  `DROP INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`, `ALTER TYPE … ADD VALUE`
  followed by use of the new value in the same migration, `VACUUM`,
  `ALTER SYSTEM` which is forbidden anyway). The parser classifies these; a
  mismatch between declaration and content is a blocking lint:
  - `transactional: true` with a non-transactional statement →
    `MIGRATION_STATEMENT_FORBIDDEN`;
  - `transactional: false` with no statement that needs it → blocking lint
    `needless_nontransactional` (non-transactional mode is strictly more
    dangerous and must be justified by content).
- Non-transactional bundles SHOULD contain exactly one non-transactional
  statement (lint `multiple_nontransactional_statements`, warn). The execution
  and partial-failure semantics are in
  [`failure-and-recovery.md`](./failure-and-recovery.md#2-non-transactional-migrations).

## 6. Project configuration `exponetdb.project.yaml`

**[DECIDED]** One file at the root of a migration stream:

```yaml
schema: exponetdb.project/v1
project: reosa/platform                 # must match the registry
layout: bundles                         # bundles | legacy+bundles (during import)
defaults:
  lockTimeout: 5s
  statementTimeout: 15m
  role: owner                           # default execution role alias for manifests without execution.role
  searchPath: ["public"]                # default for manifests without execution.searchPath
executionRoles:
  owner: reosa_owner                    # alias → PostgreSQL role the migrator SET ROLEs into
managedScope:
  includeSchemas: ["public", "status"]  # or "*"
  excludeSchemas: []                    # added to the built-in exclusions
trustedExtensions: ["pg_trgm"]
lintProfile: strict                     # strict | standard ; overrides per rule allowed
legacy:                                 # only during/after legacy import
  directory: ../migrations              # flat legacy files, read-only after import
  baseline: baseline:reosa-platform-2026-11
```

The registry is the source of truth for the project's targets and environments;
this file only describes the stream. A disagreement (for example `project`
naming a project that does not exist) is `MIGRATION_BUNDLE_INVALID`.

**[DECIDED]** (Wave 1 clarification.) `defaults` is optional and each of its
keys is optional; `defaults.role` must name an alias in `executionRoles`. The
schema `exponetdb.project/v1` in `packages/contracts` covers the fields shown
here and rejects unknown keys; required are `schema`, `project`, `layout`,
`executionRoles` (at least one alias), `managedScope` and `lintProfile`;
`legacy` is required when `layout` is `legacy+bundles`. Fields described
elsewhere but not yet shaped (bundle roots, per-rule lint overrides) are added
as optional fields in the wave that uses them (Wave 6).

## 7. Edge cases

| Case | Behavior |
|---|---|
| Two bundles with the same id in one submission | `MIGRATION_BUNDLE_INVALID` |
| Directory renamed (name slug changed) after apply | Warning `renamed_applied_migration`; checksum unaffected |
| `description` edited after apply | Allowed; not hashed |
| `dependsOn` edited after apply | Checksum mismatch; this is a different migration |
| CRLF checkout on Windows | Normalized; identical checksum |
| Comment edited after apply (outside literals) | Identical apply checksum; source digest differs; lint `comment_only_change` (info) |
| Comment edited inside a function body after apply | Checksum mismatch: the comment is part of the stored function source |
| File saved with BOM | Rejected with a clear error; author re-saves |
| `up.sql` empty | Rejected (`empty_migration`) |
| `up.sql` only comments | Rejected (`no_statements`) |
| ULID with lowercase letters | Rejected; the CLI generates uppercase. (ULIDs are case-insensitive by spec, but one canonical form avoids two directories for one id.) |
| ULID timestamp in the future (clock wrong) | Warning only; ids do not define order |
| Bundle submitted for a project different from `exponetdb.project.yaml` | `MIGRATION_BUNDLE_INVALID` |
