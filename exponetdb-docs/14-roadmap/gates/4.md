## 3. Driver spike

**[OBSERVED]** (2026-10-06) `node-postgres` (`pg` 8.23.1, already the
Control Store driver) with `pg-cursor` 2.22.1 on Node.js 24.21.0 against
PostgreSQL 16.15, 17.11 and 18.6 (`pgvector/pgvector` images with
`pg_trgm`), each with `ssl=on` and a server certificate from a throwaway CA
(`subjectAltName=DNS:pg.example.test`), plus one PostgreSQL 17 with
`ssl=off`. 68 of 68 checks passed, on every major:

| Requirement | Result |
|---|---|
| Connection, custom CA, hostname verification | `ssl: { ca, servername, rejectUnauthorized: true }` to `127.0.0.1` verifies the certificate against `servername`; `pg_stat_ssl` shows TLS 1.3 |
| Wrong CA, self-signed CA not trusted, wrong host name, IP without matching SAN | refused (`UNABLE_TO_VERIFY_LEAF_SIGNATURE`, `ERR_TLS_CERT_ALTNAME_INVALID`) |
| Plaintext server while TLS is required | refused ("The server does not support SSL connections"); never a plaintext retry |
| Simple and extended protocol | `SELECT 1` uses the simple protocol; a query with values, or `queryMode: 'extended'`, uses Parse/Bind/Execute; pipelining is opt-in (`pipeline: false` by default); the extended protocol refuses two statements in one message (`42601`) |
| Transactions, `READ ONLY` | `BEGIN … READ ONLY` refuses a write with `25006` |
| `statement_timeout`, `lock_timeout` | `57014` and `55P03` |
| Startup parameters | `options: '-c search_path= -c TimeZone=UTC'` pins the session (`search_path` empty: an unqualified `CREATE TABLE` fails with `3F000`) |
| Notices, SQLSTATE metadata | notices delivered with code; errors carry `code`, `schema`, `table`, `constraint`, `position`, with `detail` separate (so it can be dropped) |
| Cursors | `pg-cursor` reads bounded batches inside a `READ ONLY` transaction |
| Cancellation | the protocol CancelRequest (process id and secret key) ends the query with `57014` within ~300 ms |
| Hung queries | a client-side `query_timeout` errors after its deadline; the connection is then destroyed, never returned to a pool |
| Connect timeout | `connectionTimeoutMillis` bounds a black-holed connect (1 s) |
| `server_version_num` | read as an integer (`160015`, `170011`, `180006`) |
| TCP keepalive | `keepAlive` with an initial delay |

One property shapes the adapter: `pg` sets `servername` to the host itself
when the host is a DNS name and keeps a caller-supplied `servername` only
for an IP host. The registry therefore requires, for a DNS host, the TLS
server name to equal the host, and for an IP host an explicit TLS server
name that the certificate names. **Decision:** `pg` + `pg-cursor`, as
planned; no architecture change. No second driver.

## 4. Parser spike

**[OBSERVED]** (2026-10-06) Maintained Node.js bindings of libpg_query
were audited: `libpg-query` (WASM, MIT, publisher `constructive-io/libpg-query-node`,
one build per PostgreSQL major: `16.7.3` built from libpg_query `16-5.2.0`,
`17.7.4` from `17-6.1.0`, `18.1.5` from the binding maintainers' tag
`18-constructive`; no install scripts, no native build, no download at
install time), `pgsql-parser` (a deparser on top of the same WASM),
`@libpg-query/parser` and `@pg-nano/pg-parser` (native, `prebuild-install`
downloads a binary at install time: refused). Upstream `pganalyze/libpg_query`
has a `18-latest` branch but no tagged 18 release at execution time; that the
18 grammar comes from the binding maintainers' tag is a recorded
supply-chain residual.

The three builds were installed side by side through npm aliases and run
on Node.js 24 (40 of 43 checks as written; the three misses were a wrong
expected offset in the spike itself, verified afterwards):

| Requirement | Result |
|---|---|
| Per-major grammar | PostgreSQL 18 syntax (`GENERATED … VIRTUAL`, `NOT ENFORCED`) parses with the 18 build and is refused by 16 and 17; `JSON_TABLE` (17) is refused by 16. One grammar for every target would accept syntax the server refuses or the reverse, so each target is parsed with its own major's build |
| Statements and source ranges | `stmts[].stmt_location`/`stmt_len` per statement; constants (`A_Const`) carry locations; all locations are **UTF-8 byte offsets** (and 18 reports a statement start without leading whitespace, 16 and 17 with it) |
| Classification | node types per statement (`SelectStmt`, `CreateStmt`, …); a data-modifying CTE is visible as a `DeleteStmt` under `withClause`; `FOR UPDATE` as `lockingClause` |
| Errors | a syntax error is a typed `SqlError` with a cursor position; the module stays usable afterwards |
| Hostile input | 5,000 nested parentheses parse in milliseconds; 20,000 to 1,000,000 fail as a typed `SqlError` ("memory exhausted") without crashing the process; a 20,000-element `IN` list parses in 30 to 65 ms |
| **NUL** | the parser reads a C string: `SELECT 1\u0000; DROP TABLE t` parses as one statement. Admission therefore refuses any text containing U+0000 before parsing |
| API per build | 16 and 17 export `parse` only; 18 adds `normalize`, `scan`, `fingerprint` and PL/pgSQL parsing. Redaction normalizes from the parse tree and ExponetDB's own PostgreSQL lexer on every major instead of the 18-only `normalize`; PL/pgSQL parsing on 16 and 17 is a Wave 6 question, not needed in Wave 4 |

**Decision:** `libpg-query` per major (`16.7.3`, `17.7.4`, `18.1.5`),
pinned exactly through npm aliases, loaded lazily per major inside
`packages/postgres/src/parser` (the boundary component of
`package-architecture.md` §2).

## 7. Residual risks

- **Physical clones.** A standby or base-backup clone carries the same
  `system_identifier` and marker; a promoted clone behind a re-pointed name
  with a certificate from the registered CA is indistinguishable. Writes
  from Wave 6 also bind the marker's generation.
- **Marker tampering by an owner.** A superuser or the marker table's owner
  can disable its triggers; the health sampler detects a changed or missing
  marker and suspends the target, after the fact.
- **Extension membership.** Decided by the owner on 2026-10-07 (R1, §9.3):
  member identities are hashed. Remaining: the structure of a member is not
  hashed (a table moved into an extension shows as moved, later changes
  inside it do not), and a superuser can change an extension's own members.
- **Existence of targets for restricted tokens.** Decided by the owner on
  2026-10-07 (R2, §9.3): `TARGET_NOT_FOUND`, implemented in §9.
- **Control Store compromise (T11).** A writer to the Control Store can
  replace a stored document together with its digest.
- **Parser supply chain.** The PostgreSQL 18 grammar comes from the binding
  maintainers' tag, not a tagged upstream release (§4).
- **Deparse changes within a major.** A PostgreSQL minor release that
  deparses differently would change fingerprints; the golden vectors would
  fail first.
- **Not implemented in Wave 4** (planned): `drift.accept`; a project scope
  change takes effect for drift with the next baseline; credential
  generation and rotation; `pg_use_reserved_connections`; per-consumer
  endpoints; the SDK is not published.
- **Measurements** come from a development container; CI prints its own.
- **Nothing is deployed.** G2 real deployment evidence is still outstanding;
  no real target was registered, no REOSA database was touched.
