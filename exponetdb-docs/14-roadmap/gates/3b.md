## 2. Standards audit

**[OBSERVED]** (2026-10-06, before implementation; sources fetched from the
official sites.)

| Standard | Version found | Notes |
|---|---|---|
| MCP specification | 2026-07-28 (final, newest final release) | A later `draft` revision exists; its authorization pages match 2026-07-28 except that the client-registration example uses `http://[::1]:3000/callback` instead of `http://localhost:3000/callback`. No delta to frozen contracts or to this design. |
| OAuth 2.1 | `draft-ietf-oauth-v2-1-16` (2026-09-03), Internet-Draft | Not an RFC; documented as a draft. |
| Client ID Metadata Document | `draft-ietf-oauth-client-id-metadata-document-02` (2026-07-06), Internet-Draft | Not an RFC. Requires no redirects, refusal of RFC 6890 special-use addresses, simple string comparison of the URL, no shared-secret auth methods; recommends a 5 KB read limit (the order sets 64 KiB, §5 D3). |
| RFC 8414, 8707, 9207, 9728, 7009, 8252, 7523, 7591, 8628, 9700 | published RFCs | unchanged |

Consequences recorded before implementation:

- MCP 2026-07-28 requires an authorization server to provide **at least
  one** of RFC 8414 metadata or OpenID Connect Discovery, and clients try
  RFC 8414 first. OIDC Discovery 1.0 requires `jwks_uri`,
  `subject_types_supported` and `id_token_signing_alg_values_supported`,
  which ExponetDB (no ID tokens, no OIDC) cannot state truthfully. ExponetDB
  therefore does not serve `/.well-known/openid-configuration` (§5 D2).
- `iss` in the authorization response is a SHOULD in MCP 2026-07-28 and
  RFC 9207; ExponetDB returns it on every authorization response, errors
  included, and advertises `authorization_response_iss_parameter_supported`.

## 4a. Adversarial self-review

**[OBSERVED]** (2026-10-06) An independent read-only review of the whole
Wave 3B diff (authorization server, engine, database guards, HTTP layer,
application, Web App, CLI) looked for exploitable defects. It found nothing
critical or high; what it found and what was done:

| # | Finding | Severity | Resolution |
|---|---|---|---|
| R1 | Client-assertion attempts were counted on a second pool connection while the token request held its transaction: ten concurrent junk assertions naming a known service client (no valid signature needed) could exhaust `serve`'s pool | medium | Fixed: attempts are counted before the transaction opens (`countAssertionAttempt`), at the token, revocation and device endpoints. Test: "never holds one connection while waiting for another: concurrent assertions cannot stall the pool" (16 concurrent requests on a 4-connection pool) |
| R2 | The assertion bucket was keyed by the (unverified) client only: anyone could lock a service account out of token issuance | low | Fixed: keyed by client and caller address (keyed pseudonym). Test: "counts assertions per client and address: another address cannot lock the client out" |
| R3 | A verified assertion stayed unspent when the device endpoint (assertion client) or the revocation endpoint (API key) refused after authentication | low | Fixed: both refuse before verifying. Test: "spends an assertion used for a refused request, and never verifies one an endpoint cannot use" |
| R4 | A device poll racing an approval could answer `invalid_grant` and leave an active grant without tokens | low | Fixed: the poll answers `authorization_pending` and the next poll issues the tokens. Test: "never loses an approval that lands while a poll reads: pending, then tokens (no orphaned grant)" (the approval is forced between the two reads) |
| R5 | One address could fill the 50 pending DCR slots | low | Mitigated: at most 3 pending registrations per requester; residual in the threat model (many addresses can still fill the pool for up to 7 days; approved and CIMD clients are unaffected) |
| R6 | `private_key_jwt` accepted the token endpoint URL and arrays as audience | low (hardening) | Fixed: `aud` must be exactly the issuer as a single string (draft-ietf-oauth-rfc7523bis, audience injection); `oauth4webapi` sends exactly that. Tests: "refuses forged, foreign, expired and unbounded assertions" (token endpoint and array audiences refused) |
| R7 | The database did not bind redirect URIs, grant types, application type and keys to the fingerprint, and `serve` could change a first-party client | low (defense in depth) | Fixed in the not yet accepted Wave 3B bundle: such a change needs a new fingerprint; a first-party client changes only through a bundle (disabling stays possible). Test: "never changes security metadata under the same fingerprint, and keeps first-party clients fixed", key swap in "disabling a service identity …" |
| R8 | Device-code phishing can reach every scope the first-party CLI may hold, human-only ones included | design | The device page now warns against codes sent by someone else; elevated scopes need a fresh proof. Whether to restrict the device flow further is decision D13 |
| R9 | The grant listing filtered and limited in application code | minor | Fixed: state filter and limit in SQL |
