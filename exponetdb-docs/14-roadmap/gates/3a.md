## 2. Implementation map

**[DECIDED]** (2026-10-05, preflight of Wave 3A; refined as the wave
proceeds, the final state is in §3.)

Preflight facts that shaped the design:

- `main` was at `62c819e` (`davdxpx/ExponetDB#5`); nothing landed after it.
- The Control Store runner applies every pending bundle first and verifies
  afterwards, so a Wave 2 `verify.sql` runs against the final schema of a
  fresh installation. The `operations` bundle's `verify.sql` pins the number
  of triggers in the `operations` schema (13) and the policy bundle pins the
  triggers on `policy.rule_settings`. New tables with triggers therefore go
  into new schemas (`auth`, `approvals`), never into `operations`, and no
  Wave 2 object they check is altered.
- `exponetdb.audit/v1` is a hashed contract; Wave 3A adds actions (an open
  set) and uses the existing members (`client.sessionId`, `changes`,
  `request.ipHash`), never new members.
- `pv1` hashes rule ids, rule versions and effective configuration; new
  rules change the inputs, never the construction.
- The audit pseudonymizer existed without a key; Wave 3A provisions the key
  as an `auth`-consumer secret, separate from the rate-limit key.

| Area | Where | Notes |
|---|---|---|
| Contracts | `packages/contracts` | additive actions (auth ceremonies, credential self-service, identity lifecycle, access planning, approvals list), permission rules `self` and `public`, scope rule `none`, auth route contracts under `/auth`, management routes under `/api/v1`, additive error codes; generated artifacts regenerated |
| Ids | `packages/kernel`, Go conformance | new prefixes `fac_` (authentication factor), `cap_` (one-time capability), `chl_` (authentication challenge), `rau_` (re-authentication event); vectors appended |
| Control Store | new bundles `auth-identity`, `access-control`, `plan-approvals` | schemas `auth` and `approvals`; Wave 2 bundles untouched |
| Identity and authentication | `packages/auth` | identities, factors (passkey, password, TOTP, recovery codes), challenges, capabilities (setup, invitation, recovery), sessions, CSRF, re-authentication, rate limits, notifications, bootstrap, out-of-band recovery |
| RBAC and authorization | `packages/auth` (`rbac/`, `authorization/`) | built-in role matrix, scope coverage, subject resolver port, central two-phase engine; policy rules in `packages/policy` |
| Operations | `packages/operations` (approvals, re-apply after cooling, authorization re-check hooks), `packages/auth` (access kinds) | one state machine; approvals in their own schema |
| Use cases | new `packages/application` | the layer interfaces call (C-9) |
| HTTP | `apps/server/src/interfaces/http` | middleware, `/auth/*` ceremonies, `/api/v1` management resources, security headers |
| Web | new `apps/web` | minimal auth shell: no framework, no third-party scripts, strict CSP |

Dependency edges added to the documented graph (reason in
[`package-architecture.md`](../../01-architecture/package-architecture.md)):
`auth → policy` (the `principal` and `access` fact providers implement the
policy package's interfaces), `auth → operations` (the access operation
kinds are the auth package's kinds, as migrations, nodes and backups own
theirs), `application → auth, operations, policy, control-store, audit`.
