# Open decisions raised by the dress rehearsal (agent S5)

1. **S5-D1 (lint tier vs evidence):** a bundle verified on staging can be lint-blocked at production (the production lint is strict: `CREATE INDEX` without `CONCURRENTLY`, a type change and a drop are blocking). With the linear chain `migration new` creates, one hazardous bundle blocks every later one from production, and fixing it means a new checksum that must be verified on staging again. Options: lint at the production tier on evidence applies; an approved lint override on production; keep and teach. S5 recommends running the strict lint in the nonprod apply path as a warning that names "blocks production".
2. **S5-D2 (drift.accept granularity):** whole target only today, REST and Web App only (no CLI). Decide per-finding or per-operation accept, and a CLI command.
3. **S5-D3 (endpoint changes):** pre-validate identity at plan time (system identifier) and decide whether a foreign instance should suspend targets (today yes, fail closed) or only block writes.
4. **S5-D4 (REOSA move between providers):** build `target.rehome` (re-stamp, generation + 1) or declare import-after-move the only route and fix `legacy-import.md` §5.
5. **S5-D5 (plan actor binding):** a plan made with the CLI cannot be applied in the Web App session (`PLAN_BINDING_ACTOR` 403). Intended? Decide whether approvals-only in the Web App is the rule.
6. **S5-D6 (Wave 11 prerequisite):** destructive production bundles need a product-managed verified backup (node agent + adopted pgBackRest repository on reos-db-01; the storage part of OD-4 is open). Confirm the prerequisite, or decide that destructive bundles go through break-glass once OD-21 is decided.
7. **S5-D7 (CREATE PUBLICATION):** allow plain table publications in bundles and replay (`supabase_realtime` is standard on Supabase), or keep it forbidden with an explicit `notApplicable` + `unmanaged_but_present` convention.
8. **S5-D8 (plan size cap):** 50 inline bundles and 200 stored ids per plan, and CLI batching: keep and document, or raise.

What the rehearsal showed (PASS with findings; PostgreSQL 17, then 16 and 18 for import, baseline, plan and apply): 306 tables, 165 RLS tables, 402 policies, 71 functions, 4.4 GB; the 150-file hostile history was analysed in 21.6 s (worker RSS 173 to 265 MB) and every hostile file was found (16 items to decide); baseline 7.5 s; apply under pgbench (8 clients, 300 tps): p99 6 ms before, **8.75 s during** the 16.6 s apply (an index build on 5M rows and a type change on 1.5M rows), 4.8 ms after, 0 failed queries, 48 percent of window transactions over 1 s — the plan's lock-risk text matched; drift: 5 of 6 out-of-band changes seen (the table comment is not); PITR in place to before the last bundle: RTO 13.4 s to accepting connections, RPO 0 against the target (105 of 105 marker commits), consistent again after 72 s with `ledger reconcile` (3.9 s, no approval on nonprod); a crash with only base backup and archive: RTO 16.3 s, **RPO 12.0 s** (12 commits and one bundle lost), 4 min 24 s until re-pointed, reconciled and re-applied; promotion refused a never-verified checksum and an altered bundle with the same id; I10 replay of 149 files + 12 bundles into an empty database took 8.9 s and the `fp1` diff (+7 -7 ~6) is fully explained; 100 targets registered in 636 s (6.35 s each, flat); paging of 113 targets and 16,272 findings exact for page sizes 1 to 5000. TEMPLATE and `pg_dump` clones were refused at registration; nothing was ever executed on a wrong target.

NOT RUN by S5: product-managed backups and drills (no node agent on that stack; plain `pg_basebackup` + WAL archive was used), reconcile and PITR on a production-tier target, a Web App list at 10,000 rows (no browser), 5,000 bundles, concurrent applies, the verified-then-restored evidence target (I12). Timings are single runs.
