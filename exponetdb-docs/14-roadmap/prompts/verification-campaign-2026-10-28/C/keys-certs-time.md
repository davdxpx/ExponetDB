## 3. Clock behaviour (forward jump, back jump)

Scale of the question: 289 SQL occurrences of `now()`/`clock_timestamp()` against 83 uses of the process clock in the packages
I grepped (`auth` 127 SQL / 28 process, `operations` 15 / 5, `nodes` 16 / 23, `application` 12 / 25, `backups` 22 / 12, `diagnostics`
60 / 31). Most process-clock uses are `newId(prefix, nowMs)` (ULID time part: harmless). The ones that **decide** something:

| Check | Clock | Jump forward by Δ | Jump back by Δ |
|---|---|---|---|
| Plan `expiresAt` (create) vs apply/sweeper (`plans.ts:166,176`, `accept.ts:179-184`) | create: serve/worker process; judge: DB | plans created while the host runs ahead are valid Δ **longer** than their class limit in DB time (a 15 min `critical` plan with Δ = +1 day lives 1 day; the DB `CHECK` is relative to `created_at`, which is the same wrong clock) | plans expire Δ early; Δ ≥ lifetime means every new plan is `PLAN_EXPIRED` at apply |
| Enrollment token reveal window (`tokens.ts:79`, trigger on DB clock) | create: process; judge: DB | window Δ longer | window Δ shorter, possibly already closed |
| Node reads `offline` (`views.ts:58-71`) | read time: **serve process** vs heartbeat time written by the DB | all nodes read `offline` when Δ > 60 s; flapping at the margin | nodes read live for Δ longer after they stopped |
| Node certificate `notBefore/notAfter`, `renewDue` (`gateway.ts:119-125,279-285`) | gateway process clock | `notBefore = now − 5 min` in the future for a node whose clock is behind → handshake refused as not yet valid; renewal instruction too early | certificates shorter than 72 h in real time; renewal late |
| Agent `DueForRenewal` (`enroll.go:303-312`) | agent host clock | renews early (harmless) | renews late: a host clock Δ behind loses Δ of the 24 h window |
| Job envelope `notBefore/expiresAt` (`jobs.ts:103`) | worker process vs agent clock | agent refuses (`clock_untrusted` or expired) | agent accepts a job the Control Plane already considers expired by at most Δ |
| Operation lease belief (`driver.ts:96-110`) | `Date.now()`, wall clock, **not monotonic** | a step jump of Δ > 10 s makes `Date.now() >= heldUntil − renewMs` true after any failed renewal → the step aborts although the DB lease is held | after a failed renewal the worker keeps executing up to Δ past the DB expiry; a second worker may take over, both execute (the writes are fenced by `leaseHeld`, the target-side execution is not) |
| Lease/claim/heartbeat/session/step-up/OAuth/API key/break-glass/idempotency/audit `occurred_at` | DB `clock_timestamp()` | immune to the application host clock | immune; audit time is monotone along the chain by construction (`writer.ts:74-77`, `greatest(clock_timestamp(), head.occurred_at)`) |
| `private_key_jwt` assertion `exp/iat` (`oauth/assertion.ts:69`) | process | assertions look expired or from the future (skew 60 s) | accepted up to Δ after expiry (max assertion life 300 s) |
| S3 SigV4 signing, object-lock retention (`audit/export/s3.ts:123,164`) | process | the object store answers `RequestTimeTooSkewed` (>15 min): export fails, mutations continue | same |
| Health history gaps, drift scheduling, sampler | DB `clock_timestamp()` for stored times; "never later than the Control Store's clock" (`health.md:344-347`) | n/a | n/a |
| Password hashing/rate limits | DB | immune | immune |

There is **no clock-skew self-check**: `self-observability.md:91` lists "clock skew between processes and the Control Store" and `:107`
says it is not covered. The agent reports `clockSkewMs` from the gateway's `serverTime` (`agent.go` `observeServerTime`, `views.ts:76`),
which covers hosts, not `serve`/`worker`. C1-7.

## 4. STACK STEPS

1. **API key expiry/listing.** Create a service account and a key with `--days 1`; as the DB owner `UPDATE oauth.api_keys SET created_at = created_at - interval '2 days', expires_at = expires_at - interval '2 days'` is refused by the guard trigger, so instead wait or use `date -s` on the **Control Store host** (see 6). Expected after expiry: bearer call → 401 `invalid_token`; `GET /api/v1/service-accounts/{id}/api-keys` shows `keyState: "expired"`; `api_key revoke` succeeds. Read `grep expiring` over the CLI help to confirm there is no expiring filter.
2. **Master key rotation order (C1-8).** `exponetdb keyring generate --key-id k1 --output k1.json`, run the stack on it, create a TOTP factor. `keyring add-key --input k1.json --key-id k2 --output k2.json`; restart **only the worker** with `k2.json`; wait 11 min; then `curl $S/healthz/detail`, log in with TOTP on serve (expected: readiness `keyring` `fail keyring_missing_key`, login error `secret_key_unavailable`). Then restart serve with `k2.json`, `exponetdb keyring status` expect `k1 references 0 removable true`, drop `k1`, restart all three, expect `ready`.
3. **Audit pseudonym key.** `exponetdb keyring rotate-mcp-key --purpose mcp.cursor_key` works; confirm `--purpose audit.pseudonym_key` is `invalid arguments` (exit 2).
4. **MCP key rotation.** With a client holding a cursor from `targets_list`, run `rotate-mcp-key --purpose mcp.cursor_key`, wait 5 min, use the old cursor: expected still accepted (previous version opens); after a second rotation: refused.
5. **Node certificate renewal window (TC-042 host part).** On the host stack: `exponetdb-node status` (expect remaining life ~72 h after enrollment). Stop the agent for 47 h of **host clock time** by `systemctl stop exponetdb-node; date -s '+47 hours'; systemctl start exponetdb-node`, expect `certificate renewed` within one loop turn and `node.certificate_renewed` in `GET /audit-events`. Repeat with `+73 hours` while stopped: expect the agent log to show the refused handshake, gateway log `agent.tls_refused`/`agent.refused`, `GET /nodes/{id}` state `offline`, `exponetdb-node status` `EXPIRED … ago`. Recover with decommission + new enrollment token; time the steps and count the commands.
6. **Clock jump forward on `serve` (C1-7).** `docker run --rm --privileged` is not needed: use `libfaketime` or a VM with `date -s '+2 hours'` for the serve host only. Create a `critical` plan (default 15 min lifetime) and read `expiresAt`; compare with the DB clock `SELECT clock_timestamp()`. Expected: `expiresAt - clock_timestamp() ≈ 2 h 15 min`. Apply it 90 minutes later in DB time: expected success (it should have expired). Then jump back by 2 h and create a plan; expected `PLAN_EXPIRED` at apply within seconds.
7. **Nodes flap on a skewed serve (C1-7).** With serve +2 min: `GET /api/v1/nodes`; expected every `active` node reads `offline`. Revert.
8. **Lease belief on a wall-clock step.** Run a 3 min operation (`pg_sleep` migration); mid-way `date -s '-5 min'` on the worker host while blocking the worker's Control Store connection for one renewal (`iptables DROP` for 12 s): observe `operations.operation_events` kinds `lease_*`; expected the step continues past the DB lease expiry (30 s) with the first worker; a second worker's `lease_taken_over` event appears while step 1 is still running.
