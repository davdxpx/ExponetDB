# TC-009 `latest` and `older` restore drills always fail on a real host

Verdict: FIXED (helper level with the shipped, sandboxed helper under systemd, and Control Plane level), plus a neighbouring weakness of the "reached the end" check.

## Setup
Disposable cx33 `vc-2`, Ubuntu 24.04, PostgreSQL 17.11 (PGDG, cluster `17/exdbnode`), pgBackRest 2.60.0 (encrypted posix repository), restic 0.16.4. The node agent and root helper ran as the shipped systemd units inside a privileged systemd container (`r1-host`) built from the same packages; release binaries built with `agent/node/packaging/build.sh 0.7.0` from `d51da5d0` (new) and `d0229550` (old). Driver: the first campaign's `labctl` (signed jobs over the helper socket), script `t9r1.sh`.

## Original reproduction and the finding's matrix against real pgBackRest 2.60 (`restore.execute`, targets exactly as the Control Plane sends them)
| target | old helper | new helper |
|---|---|---|
| `{label:<newest>, timeline:1}` (what `latest` sends) | `failed`, exit 31 in 1.6 s (`option 'target-timeline' not valid without option 'type'`) | `succeeded`, recovery reached `0/B000000` = the end of the archive, row count correct |
| `{label:<older>, timeline:1}` (`older`) | exit 31 | `succeeded`, reached the end of the archive |
| `{label:<newest>}` alone | `succeeded` but stopped at `0/12000088` (end of the backup, archive ended `0/15000000`) | `succeeded`, reached the archive end |
| nothing, nothing + timeline | `succeeded` | `succeeded` |
| label + time + timeline (`pitr`) | works | `succeeded`, reached the target time |
| time only | works | works |
| lsn (a record boundary), with and without timeline (`t9lsn.sh`) | n/a | `succeeded` both, rows as expected |
(An LSN that is not a record boundary, `pg_current_wal_lsn()` right after a WAL switch, fails with `recovery ended before configured recovery target was reached` in both versions: a PostgreSQL property, not a defect.)

## Control Plane level (probe `probes/r1-cp-backup.host.test.ts`, real serve/gateway/worker, agent and helper as systemd units, real engines)
New: drills `latest` (RTO 4 s), `older` (4 s), `pitr_random` (3 s) all end `passed`, `restoreState discarded`, `recovery_target_reached passed`. Old: `latest` and `older` end `verification_failed` after 6 s (`checks` only `fingerprint`, `ledger_head`), `pitr_random` fails on amcheck (TC-010).

## Acceptance tests
Go: `TestRestoreTypeArgs` (eight cases and two invariants), helper package green; the finding's `pglab` matrix against real pgBackRest was not added by the fix (the commit says so) and CI's `pglab` run does not cover the sandboxed units; I ran the matrix and the host scenario myself (above). Fails-before: the old helper fails A and B with exit 31 in the same harness; the unit test fails on the old `restore.go` (assertion text in the commit).

## Diff review
`restoreTypeArgs` gives `--type=default --set=<label>` for a label alone; `--target-timeline` only with `default`, `time`, `lsn`; `immediate` stays only in the human runbook (`runbook.ts:260`). No skip, no weakened assertion. Untested: a source cluster that switched timelines (the Control Plane pins `--target-timeline=<backup's timeline>`, which stops a `default` replay at the end of that timeline).

## Neighbour: the "reached the end of the archive" check
`walTo = segmentLsn(maxSegment)` is the START of the newest archived segment (`selection.ts:98`, `records.ts:323-328`), and `replayShort` is `reached < walTo` (`kinds.ts:1356-1361`). In the real run `reached` was `0/B000000` against a newest segment `..0A` (`walTo` `0/A000000`). A replay that stops anywhere inside the newest segment passes. See the finding "The restore drill's replay check compares with the start of the newest segment".
