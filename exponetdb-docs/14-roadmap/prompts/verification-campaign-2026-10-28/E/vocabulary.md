# E1: vocabulary across CLI, REST, MCP, Web App and docs

Block E, item 2 (static). Sources at `d51da5d0`: the 178 CLI commands
(`exponetdb commands`, `exponetdb-docs/15-cli/reference.md`, identical to the registry); the
265 actions of `packages/contracts/generated/catalog.json`; the 30 MCP tools of
`packages/contracts/src/mcp/tools.ts`; the typed message keys of `apps/web/src/lib/i18n/messages/*.ts`;
`exponetdb-docs/02-control-plane`, `04-migrations`, `12-operations`, `09-backups-and-restore`.

"Wrong action?" answers the brief's question: *could this inconsistency make an operator do the
wrong thing* (Y/N) and why. A **Y** that is a code or doc fix is a finding (VOC-n in
`../F/findings-E1.md`), the rest are polish.

## 2. Names that differ between surfaces for the same action

| Meaning | CLI | MCP | REST action id | Web App |
|---|---|---|---|---|
| list a target's sessions | `session list` | `sessions_list` | `session.list` | Connections |
| cancel a running query | `session cancel` | `sql_cancel` | `query.cancel` **and** `connections.cancel` | "Cancel query" |
| read an object's definition | `schema show` | `schema_inspect` | `schema.object.get` | Schema browser |
| plan a rollback | `migration rollback` | `migration_rollback_plan` | `migration.rollback.plan` | "Roll back" |
| re-check an applied migration | `migration verify` | `migration_verify` | `migration.verify` | (no button found) |
| verify an operation again | `operation retry-verification` | (none) | `operation.retry_verification` | "Verify again" (only if `retryable`) |
| apply a stored plan | `plan apply` | `plan_apply` | `plan.apply` | "Apply" |
| create + apply from local files | `migration apply` | (none; `migration_plan` + `plan_apply`) | `migration.plan` + `plan.apply` | (none) |
| approve | `approval approve` (opens the browser) | (none; humans only) | `approval.approve` | "Approve" |
| accept drift | (none) | (none) | `drift.accept.plan` + `plan.apply` | "Accept drift" |
| activate break-glass | (none; `--break-glass` consumes one) | (none) | `breakglass.activate` | Break-glass page |
| force-release a lock | (none) | (none) | `operation.force_release` (registered, not built) | (none) |
| store a bundle | (none; done by `migration plan`) | (none) | `migration.bundle.ingest` | (SQL editor drafts) |

Two rows matter most: **verify** is two server actions with two CLI names and one Web button, and
the CLI never says which one an operation in `needs_attention` needs; **`migration apply`** exists only
in the CLI as a composition, so its "plan" is not the one a person reviewed with `migration plan`.

## 3. Where documents contradict the code's vocabulary

* `authoring-and-ci.md:83,86` (`migration apply <planId>`, `lock-key`): the table is the Wave 0 design and
  the paragraph above it (68-73) says so; harmless but unreliable if copied (VOC-1).
* `concurrency.md:88-89` `[DECIDED]`: "the key derivation is published (this document, and the CLI command
  `exponetdb lock-key <target>`)": **no caveat**, and `authoring-and-ci.md:73` says `lock-key` "is not built".
  The lock keys can only be derived by hand (`packages/postgres/src/ledger.ts:21-25` has the formula, which
  matches the doc).
* `bootstrap.md:136-140` `exponetdb ca init-root`, `exponetdb ca issue-intermediate`: no such command
  in either binary; the working command is `exponetdb node-pki init` (server).
* `local-development.md:18,42` `exponetdb dev`, `exponetdb dev seed`: only `dev up|status|owner|…`
  exist (no `dev seed`).
* `backup-runbooks.md:24` names the protection reason `archive_stale`; the code's reasons
  (`packages/backups/src/protection.ts:143-271`) are `wal_archive_failing`, `wal_gap`,
  `catalog_stale`, `rpo_above_objective`, … `archive_stale` does not exist.
* `policy-engine.md` lists `migration.checksum-consistent`, `migration.dependencies-satisfied`,
  `migration.pg-version`, `migration.execution-role` as rule ids; the policy registry
  (`packages/policy/src/catalog`, 45 ids) has none of them (the checks run in the planner and surface
  as `MIGRATION_CHECKSUM_MISMATCH` or as a `requirementsUnmet` fact).
* `operations-engine.md` §4.1 calls it `operation.retry_verification` and the CLI `retry-verification`;
  `verification.md:497` still restricts it to two kinds while `:498-` extends it to four.
