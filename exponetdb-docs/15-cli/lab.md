A disposable ExponetDB installation on this machine's Docker, for
development and for the owner's tests. A fresh clone with Docker gets its
own environment with one documented command; it never touches anything it
did not create, and it is never the installation at `db.exponet.cloud` or
anything registered there.

## 1. Quick start

```sh
exponetdb dev up                         # inside an ExponetDB checkout: builds the image at HEAD
exponetdb dev test smoke                 # checks the running lab
exponetdb profile add local --server http://localhost:8480
exponetdb dev owner --email you@example.test --open
exponetdb login --profile local
```

`dev up --image <ref>` uses an ExponetDB image built elsewhere instead of
building one (CI uses the image it just built).

## 2. What `dev up` creates

All on a private Docker network `exdb-lab-<id>`; only `serve` is published,
on `127.0.0.1:<port>` (default 8480).

| Role | Image | What it is |
|---|---|---|
| `control` | `postgres:17.11` (pinned by digest) | the Control Store, a plain PostgreSQL 17 reached only on the lab network |
| `staging`, `production` | `pgvector/pgvector:pg16`, `pg17` or `pg18` (pinned; `--postgres`, default 17) | two managed targets, separate from the Control Store, with TLS: on its first start each target creates a CA and a server certificate for its container name in its own volume, and its pg_hba refuses plaintext over TCP |
| `serve`, `worker`, `gateway` | the ExponetDB image | the three process roles, each with its own login |

The installation is set up the way an operator sets one up
([`bootstrap.md`](../12-operations/bootstrap.md)): the image's own
bootstrap SQL (SCRAM verifiers only) applied by the Control Store's
superuser, `control-store migrate` with the migration login in a one-off
container, a keyring generated by the image, then each role with its own
login. `dev owner` runs `bootstrap owner` of the same image with the
serve login; the setup link goes into a new 0600 file (or, with `--open`,
straight to the browser) and is never printed.

Registering a target uses the lab network's names: host
`exdb-lab-<id>-staging` (or `-production`), port 5432, TLS `verify-full`,
the CA bundle `dev status` shows. The roles script a cluster registration
generates is applied with `exponetdb dev sql staging --file <script>`, the
lab's equivalent of the one-time superuser step of `bootstrap.md` §5.

**[OPEN]** A node (the Go agent on a systemd host) is not part of `dev up`:
the agent needs root and systemd on its database host. Node scenarios run
with `dev test host:<scenario>` on a disposable systemd host as root
(§5), the same entrypoint as CI.

## 3. Image and source

`dev up` without `--image` finds the ExponetDB checkout around the working
directory (or `--source <dir>`), reads its commit (`-dirty` when the tree
has changes) and builds the repository's own Dockerfile with that commit as
`EXPONETDB_BUILD_COMMIT`, tagged `exponetdb-lab:<commit>`. A clean commit
whose image exists is reused; a dirty tree is always rebuilt. The build log
is in the lab's `work/build.log`.

The lab records the commit. When the checkout moves on, `dev status` shows
both, and `dev up` refuses to start the old image unnoticed (`lab_stale`):
`--rebuild` builds the current source, runs `control-store migrate` with it
and replaces the three process roles (the databases keep their data);
`--keep-image` starts the recorded image knowingly.

`docker build` needs the package registry from inside the build. Where an
intercepting proxy hides it (a sandbox with its own TLS authority), build
the image elsewhere and pass `--image`.

## 4. State, labels and ownership

| Path (below the CLI's configuration directory) | Content |
|---|---|
| `labs/<id>/lab.json` (0600) | the lab record: fixture version, image and commit, port, network and container IDs, volumes, installation |
| `labs/<id>/secrets/` (0700, files 0600) | superuser passwords, the bootstrap credentials, the keyring, the role environments, the owner setup link |
| `labs/<id>/tls/` | the targets' CA certificates (public) |
| `labs/<id>/runs/<run>/` | one directory per test run: `record.json` and `output.log` |
| `labs/<id>/work/` | the image build log |
| `lab-exports/<id>-<time>/` | exports; kept after `destroy` |

The state is outside any repository, so nothing of it can be committed.
**[DECIDED]**

- Every network, volume and container carries the labels
  `cloud.exponet.lab.fixture`, `.id`, `.role` and `.owner` (a hash of the
  state directory). A command acts on the container IDs recorded in
  `lab.json`, after checking all of them: the labels, the name, no bind
  mount (so no Docker socket and no host directory), only the role's own
  volume, not privileged. One foreign object stops the command before
  anything is changed (`lab_foreign`).
- `dev up` never adopts an object that has a lab's name but is not in the
  record; it refuses and leaves it alone.
- The CLI talks to Docker only through the local socket
  (`unix:///var/run/docker.sock`, or another `unix://` path in
  `EXPONETDB_LAB_DOCKER_SOCKET`). `DOCKER_HOST`, `DOCKER_CONTEXT` and the
  TLS variables are removed and the default (local) builder is used, so a
  remote daemon or builder is never used by accident.
- The roles get their secrets through `--env-file`. Anyone who may use the
  Docker socket can read a container's environment; that access is
  root-equivalent on the machine anyway. `dev export` never writes a
  container's environment or command line.
- Containers on a shared kernel are development evidence, not a VM
  boundary.

## 5. Commands

| Command | What it does |
|---|---|
| `dev up` | create the lab, or start a stopped one (refuses a stale image, §3) |
| `dev status` | every role's state and readiness (database over TCP, Docker health, serve `/healthz/ready`), the image against the source, the active run and, separately, the last finished run; exit 0 only when ready |
| `dev owner --email <address>` | the first-owner setup link into a new private file (`--open`, `--reissue`) |
| `dev logs <role>` / `dev logs --run <run>` | a role's container log (`--tail`, `--since`, `--follow`), or one run's own log |
| `dev shell <role>` | a shell in a lab container (a terminal is needed; databases as `postgres`) |
| `dev sql <control\|staging\|production>` | psql in a lab database as its local superuser: interactive, `--file`, or stdin |
| `dev test <suite>` | a test run (below) |
| `dev runs` | the runs, newest first |
| `dev export` | logs, container facts and run records into a new directory |
| `dev stop` | stop the containers; data stays |
| `dev reset --yes` | export, then new databases and containers (same ID, image, port) |
| `dev destroy --yes` | export, then remove every object and the state |

`stop`, `reset` and `destroy` refuse while a run holds the lab
(`lab_busy`); `--interrupt` stops that run first and records it as
interrupted. `reset` and `destroy` need `--yes` (or a confirmation on a
terminal) and act only on the checked lab ID.

**Suites.** `smoke` checks the running lab: every role, TLS on both
targets (plaintext refused, the certificate verified for the target's
name), the server's probes and Web App headers, sign-in required on the
API, every role on the lab's image, and no secret material in the process
roles' logs. The other suites run the repository's own entrypoints from
the source checkout, the same commands as CI and the README:

| Suite | Command | Needs |
|---|---|---|
| `unit` | `bun run test` | the checkout |
| `integration` | `bun run test:integration` | `EXDB_TEST_PG_URL`, `EXDB_TEST_TARGETS` (from `tooling/dev/control-store.sh` and `tooling/dev/targets.sh`) |
| `install` | `bun run --cwd apps/cli test:install` | Node 24, npm |
| `host:<scenario>` | `bun run --cwd apps/server test:host test/host/<scenario>.host.test.ts` | root and systemd on a disposable host, `EXDB_TEST_PG_URL`, `EXDB_NODE_CLUSTERS`, `EXDB_NODE_E2E_AGENT_USER` (the CLI never uses sudo) |

**Runs.** Each run has an ID, the suite, the source commit, the image, the
fixture version, start and end, its state (`running`, `passed`, `failed`,
`interrupted`, `lab_unavailable`), the suite's real exit code and its own
log. One run holds the lab at a time (a lock file naming the run); a lock
whose process is gone is recorded as interrupted and released. A run whose
environment is missing ends `lab_unavailable` (exit 5), never `failed`: a
missing lab is not a product failure. A failing suite exits 1 with its own
exit code in the record. A new run always gets a new directory, and
`status` shows the active run apart from the last finished one, so an old
result never reads as the current one.
