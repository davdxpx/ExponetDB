## Release

**[OBSERVED]** `main`'s CI run on `1484bb5` (run `39480870392`) passed every
job except `Host scenario journal (systemd)`, which fails the same way on
`ab6501e` and is open ([G8 record §8](../../14-roadmap/gates/8.md#8-limits-and-open-items));
its `image` job built the image and passed the role smoke test.

The owner built the release on `reos-01` from a clean `git archive` export of
`1484bb5` (no working-tree files, no `.git`) with
`docker build --build-arg EXPONETDB_BUILD_COMMIT=1484bb55862afe26b9aaa0f3fab8197e1e896651`
(the CI `image` job's command), tagged it with its own ID and pushed it to the
loopback registry:

|---|---|
| Registry tag | `127.0.0.1:5000/exponetdb:sha256-5ce8b418aa09aa89d5a601fd774c2bdf3366787b8d576528f16a79f780e1c2e2` |
| Pulled by Coolify | `127.0.0.1:5000/exponetdb@sha256:5ce8b418…` for each role |
| Build commit reported by each role | `1484bb55862afe26b9aaa0f3fab8197e1e896651`, version `0.2.0` |

A first push from a workstation failed with `connection refused`: the registry
listens on the server's loopback only, so a push must run on `reos-01` (or the
image must be loaded there first, `docker save | ssh … docker load`, as for
Wave 6).

The release has no Control Store bundle (no change under
`packages/control-store/migrations` between `ab6501e` and `1484bb5`), so no
backup was taken before it, as in the third Wave 7 rollout.
