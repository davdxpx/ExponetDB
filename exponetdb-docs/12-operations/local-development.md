**[DECIDED]** A developer (human or coding agent) can run the whole system
locally **without any access to REOSA or any production system**.

## 1. What runs locally

| Component | Local form |
|---|---|
| Control Store | PostgreSQL 17 container `exdb-control` |
| Managed databases | disposable PostgreSQL containers: `pg16`, `pg17`, `pg18`, each with pgvector, representing targets `demo/app/staging` and `demo/app/production` plus version-matrix targets |
| `serve`, `worker`, `gateway` | one dev process with all three roles (`exponetdb dev`), hot reload; roles can also be started separately to test isolation |
| Node agent | **fake agent** from `packages/testkit` (implements the protocol, simulates capabilities with configurable latency and faults) or the real Go agent against a PostgreSQL container with the helper in a mock mode |
| OAuth | the ExponetDB authorization server itself; a dev-only seeded owner with a known passkey replacement (TOTP secret printed on seed); loopback redirect for CLI and MCP clients |
| MCP | `http://localhost:<port>/mcp`; the dev server allows `http://localhost` origins; an MCP inspector configuration is provided. **[OBSERVED]** (Wave 7) the lab serves it, `exponetdb dev mcp-client` registers a lab client that the lab's owner approves once ([`../15-cli/lab.md`](../15-cli/lab.md) §5) |
| Object storage | S3-compatible container (for backup engine tests) |

Started by one command (`exponetdb dev up` wrapping a compose file), torn down
by one command; data lives in named volumes that `dev reset` removes.

**[OBSERVED]** (Wave 6, the implemented lab, [`../15-cli/lab.md`](../15-cli/lab.md))
`exponetdb dev up` creates the Control Store (PostgreSQL 17), two managed
targets (`staging`, `production`; PostgreSQL 16, 17 or 18 with TLS) and
`serve`, `worker` and `gateway` as separate containers of one image built
from the checkout's current commit (or `--image`), on a private Docker
network, without a compose file. It differs from the table above: there is
no hot-reload process, no fake agent, no object storage container and no
seeded owner with a known credential; the first owner enrolls through the
setup link of `exponetdb dev owner` (passkey, password, authenticator app)
like on a real installation. Nodes run in the host scenarios
(`exponetdb dev test host:<scenario>`, §5b). The table above remains the
plan for what is not built yet.

## 2. Seed data

`exponetdb dev seed` creates:

- product `demo` with environments `staging` (nonprod) and `production` (prod,
  evidence from staging), project `app`, targets on the local containers;
- identities: one owner, one developer bound to nonprod, one viewer; one
  service account; one pre-approved local MCP client (**[OBSERVED]**
  Wave 7: `dev seed` does not exist; `exponetdb dev mcp-client` registers
  the lab client, which the lab's owner approves like any client, since
  nothing is pre-trusted: OD-5 (a));
- a migration stream with ~20 bundles covering every class (additive,
  destructive, non-transactional, rewrite, data migration, security change);
- a legacy-import fixture: a database with a hand-written migration history
  that has gaps, duplicates and post-apply edits (modeled on the REOSA
  findings, without REOSA content);
- findings, health history and statement statistics generated by running a
  synthetic workload for a few minutes.

## 3. Fixtures

| Fixture | Use |
|---|---|
| Migration bundles corpus | lint, checksum, DAG and analysis tests; golden vectors shared by the TypeScript production code (the server and the CLI use the same `packages/migrations/format`) and the Go conformance implementation in `agent/node` (checksums must match across languages) |
| Hostile identifiers | names with quotes, `$$`, Unicode, reserved words, 63-byte names in every object class |
| Large catalog | generator for thousands of tables, indexes and policies (plan-guard budget tests) |
| Supabase-shaped database | a database with `auth`, `storage` and Supabase roles, to test managed-scope filtering and legacy import from Supabase-hosted projects |
| Fault scripts | network partition, agent crash mid-job, Control Store restart, lock contention, statement timeout, disk full simulation (fake agent) |

## 4. Rules

- No environment variable, fixture or script points to a real host. CI fails
  if a fixture contains a non-local hostname other than documentation examples.
- The dev server prints a banner "development mode: not for real databases"
  and refuses to start with `EXPONETDB_PUBLIC_URL` on a non-localhost domain
  unless the dev flag is off.
- Coding agents working in this repository use the local stack and its MCP
  endpoint; they never receive credentials of shared environments.

## 5. What exists since Wave 2

**[DECIDED]** Until `exponetdb dev up` exists, the services the integration
suites need are started by one script. Integration suites never fall back to
an emulation and are never skipped: without their services they fail with a
message that points here.

```sh
eval "$(bun run --silent dev:control-store)"   # starts the containers, exports the variables
bun run test:integration                         # every *.int.test.ts against them
```

| Container | Image (pinned by digest, as in CI) | Variables |
|---|---|---|
| `exdb-control` | `postgres:17.11` on `127.0.0.1:55432` | `EXDB_TEST_PG_URL`: a superuser URL of the disposable server; the suites create the five Control Store roles with the production bootstrap SQL and one fresh database per suite; migrations of parallel suites take turns under an advisory lock, because the roles' connection limits are cluster-wide (production values) |
| `exdb-s3` | `versity/versitygw:v1.8.0` on `127.0.0.1:57070` (S3-compatible, Apache-2.0) | `EXDB_TEST_S3_ENDPOINT`, `EXDB_TEST_S3_ACCESS_KEY`, `EXDB_TEST_S3_SECRET_KEY`: the audit checkpoint export contract |

`bun run verify` runs every CI check of the TypeScript, integration and Go
jobs, the integration suites included. The image job is separate because it
needs a Docker daemon: `bun run smoke:image` builds the image and runs the
role-start smoke test (`tooling/smoke/roles.sh`: bootstrap SQL, migrate,
serve, worker and gateway healthy from one image, graceful shutdown, no
secret in any log), as CI does.

The generated superuser password and S3 secret are written to
`.exdb-dev-superuser` and `.exdb-dev-s3-secret` (mode 0600, git-ignored). The
S3 container keeps its data in memory; it proves the export protocol, not an
off-host store.

## 5a. Managed-target servers (Wave 4)

**[DECIDED]** (Wave 4.) The managed-target suites (`packages/postgres`,
`packages/registry`, `packages/diagnostics` and the server's registry
tests) need PostgreSQL 16, 17 and 18 as managed targets. One script starts
them, TLS only, with a CA generated for the run:

```sh
eval "$(bun run --silent dev:targets)"   # starts the containers, exports EXDB_TEST_TARGETS
```

| Container | Image (pinned by digest, as in CI) | What it is |
|---|---|---|
| `exdb-target-pg16`, `-pg17`, `-pg18` | `pgvector/pgvector:pg16/17/18` (16.15, 17.11, 18.6 with pgvector 0.8 and `pg_trgm`) on `127.0.0.1:55516`, `55517`, `55518` | TLS only: `hostssl … scram-sha-256` and `hostnossl … reject`; the server certificate names `pg.exdb.test` and `localhost`; `max_connections = 200` |
| `exdb-target-plain` | `pgvector/pgvector:pg17` on `127.0.0.1:55599` | without TLS: the plaintext-refusal tests |

`EXDB_TEST_TARGETS` names `targets.json` in the output directory
(`.exdb-dev-targets/`, git-ignored, mode 0600): the servers, the CA, an
unrelated CA, the server certificate and key (for the fault proxy) and the
superuser password, all generated for the run and used for nothing else.
The suites create ExponetDB's roles with the product bootstrap SQL
(`clusterBootstrapStatements`), fresh databases per suite, and copy fixture
databases from templates (`@exponetdb/testkit`: hostile metadata, the
REOSA-shaped synthetic schema, the 2,000-table plan-guard catalog, the
consumer-sized catalog of the fingerprint budget, and the fixtures of the
`fp1` golden vectors, which assume the superuser `postgres`). The roles'
connection limits are cluster-wide production values (migrator 2,
verifier 4: one installation's budget) while parallel suites are several
installations on one server, so the suites that run the worker against a
shared target server (`mcp-int-world`, `http-migrations`) take turns
(`withClusterTurn`, a superuser advisory lock); without it a verification
could see "too many connections" and end, truthfully, in `needs_attention`
(Wave 7 observation). Without the
variable the suites fail; they are never skipped.

Building the image locally behind an intercepting proxy needs the proxy's
CA in the build stage; keep that in a local copy of the Dockerfile, never
in the repository's (`bun run smoke:image` then runs the three-role smoke
test on the result).

## 5b. Node agent clusters (Wave 5)

**[DECIDED]** (Wave 5 Phase 5.) The node agent's integration tests (Go,
build tag `pgit`: `agent/node/internal/pgwire`, `internal/capabilities`,
`internal/helper`)
need PostgreSQL 16, 17 and 18 **as the agent sees them on a host**: the
Debian packaging layout (`pg_createcluster`, `/etc/postgresql/<major>/<name>`,
`conf.d`, `pg_ctlcluster`, the `postgresql@` unit), the agent's role
`exponetdb_node` over the local socket with `peer` authentication, and
dedicated TLS files. On a disposable machine with the packages installed
(PGDG for 17 and 18), as root:

```sh
eval "$(sudo tooling/dev/node-clusters.sh)"   # clusters `exdbnode` on 55416-55418, exports EXDB_NODE_CLUSTERS
cd agent/node && sudo -E env "PATH=$PATH" go test -race -tags pgit ./internal/pgwire ./internal/capabilities ./internal/helper
```

Go runs with the version `agent/node/go.mod` names (1.26.10); an older local
Go fetches it (`GOTOOLCHAIN`), and `govulncheck` is run with it
(`GOTOOLCHAIN=go1.26.10 go run golang.org/x/vuln/cmd/govulncheck@v1.1.4 ./...`),
never with an older runtime. The confidentiality tests (Wave 5 correction
F1) plant synthetic canaries (a `primary_conninfo` password, custom
parameters, role and database settings, foreign `pg_hba` LDAP and RADIUS
rules, a client's failed statement in the server log) in these disposable
clusters and undo them; the server log keeps the client's statement.

The script drops and recreates the clusters named `exdbnode`; it is never
run on a host with real data. The tests run as root because the helper's
part writes PostgreSQL's files; the helper runs in process with a test job
key. On a host without systemd as PID 1 (a container), a restart goes
through `pg_ctlcluster`; with systemd (the CI job `node-pg`), through
`systemctl` and the real units. Without `EXDB_NODE_CLUSTERS` the tests fail;
they are never skipped.

**[DECIDED]** (Wave 5 Phase 5.) The capability operations end to end
(`apps/server/test/agent-capabilities.host.test.ts`, a **host test**,
`vitest.host.config.ts`) run REST plans of a person through the real gateway
and worker roles, the agent built with its e2e seams (a clock assumed
synchronized) and the root helper built the same way, against the
PostgreSQL 17 cluster above and a Control Store (§5). The helper refuses root
as its caller, so the agent runs as an unprivileged OS user that the
clusters map to `exponetdb_node`:

```sh
sudo useradd --system --no-create-home --shell /usr/sbin/nologin exdbagent
eval "$(sudo EXDB_NODE_AGENT_USER='root exdbagent' tooling/dev/node-clusters.sh)"
cd apps/server && sudo -E env "PATH=$PATH" EXDB_NODE_E2E_AGENT_USER=exdbagent bun run test:host
```

The host test also plants the canaries above in the PostgreSQL 17 cluster
and checks that none reaches the Control Store, a REST answer, the agent's
or the helper's state or a log (Wave 5 correction F1); everything it
plants is undone when it passes. **[OBSERVED]** A failed run stops before
that cleanup and leaves the canaries on the PostgreSQL 17 cluster (lines in
the managed fragment, `conf.d/50-exdb-host-canary.conf`, `primary_conninfo`
in `postgresql.auto.conf`, a database setting and an `exdb_canary_*` role);
the next run then fails at its first configuration change. Recreate the
disposable clusters with `tooling/dev/node-clusters.sh` (never on a real or
shared PostgreSQL host) before running it again. Without root, `EXDB_NODE_CLUSTERS` or `EXDB_NODE_E2E_AGENT_USER` the host
test fails; it is never skipped, and it is not part of `bun run test` or
`bun run test:integration`. The restart and the failed-unit read need systemd
as PID 1 and run in the CI job `node-pg` only.

**[DECIDED]** (Wave 6, Part A §8 and §9.) The same flows also run as
**independent host scenarios** in `apps/server/test/host/` (enrollment,
config, hba, roles and TLS, job keys, crash points, partition, journal,
identity, production, secrets). Each builds its own world
(`apps/server/test/support/host-world.ts`): its own Control Store database,
agent and helper state, and a PostgreSQL 17 cluster recreated by
`tooling/dev/node-clusters.sh` before it starts, so one scenario's leftovers
never reach another. The script removes the cluster's configuration and data
directories after `pg_dropcluster`, which keeps files it did not create (a
managed fragment, TLS files, `*.exponetdb-previous` copies); a recreated
cluster that still holds such a file is refused as `fixture_stale`.

```sh
cd apps/server && sudo -E env "PATH=$PATH" EXDB_NODE_E2E_AGENT_USER=exdbagent \
  EXDB_LAB_RUN_DIR=/var/tmp/exdb-lab-runs bun run test:host test/host/crash-points.host.test.ts
```

Before a scenario, a preflight refuses with `LAB (not a product failure):
<category>` when the lab cannot run it (not root, a missing variable or
tool, low disk, a Control Store that does not answer or is shutting down, a
cluster that is not the disposable `exdbnode`). After a failed test the
same checks run again: the report says `LAB FAILURE` with the problems found
(the Control Store went away during the run, the cluster stopped) or
`PRODUCT FAILURE suspected` when the lab is healthy. With `EXDB_LAB_RUN_DIR`
each scenario writes `<scenario>.json` (`running` with the process id while
it runs, then `passed`, `failed` or `lab_unavailable` with the failed tests
and lab problems): a record that says `running` for a process that is gone
is an interrupted run, never a result. The CI job `node-host-scenarios` runs
each scenario on its own runner with systemd as PID 1.

**[OBSERVED]** (Wave 3A, G3A accepted 2026-10-06.) The browser


--cwd apps/web build`), run `serve` with `EXPONETDB_PUBLIC_URL=http://localhost:8080`
(plain `http:` is accepted only on a loopback host), and issue the setup
link with `exponetdb bootstrap owner --email owner@example.test` and the
`exdb_serve` login. Only synthetic addresses (`@example.test`) are used in
development and tests.

also one a script catches (the page's `securitypolicyviolation` events are
written to the console the suites watch): zod runs jitless for that reason
(`apps/web/src/app/zod-jitless.ts`). The server bundle
(`bun run --cwd apps/server bundle`) and the image copy `apps/web/dist`
(`/app/web` in the image); `serve` answers every page path with its
`index.html` ([ADR-0031](../01-architecture/adr/0031-web-app-serving.md)).

**[OBSERVED]** (2026-10-13, `packages/auth/src/sessions.ts`,
`apps/server/src/interfaces/http/api.ts`, the order §5.2)
The constraint that shapes the dev setup: a cookie-authenticated mutation
needs the exact `Origin` equal to `EXPONETDB_PUBLIC_URL`, `Sec-Fetch-Site:
same-origin` and an `x-csrf-token` equal to the CSRF cookie, and every
session cookie is `__Host-` prefixed (Secure, no `Domain`, path `/`).

**[PLANNED]** A Vite dev server therefore has to run at, or be proxied as,
the configured public origin:

- run it at `http://localhost:<port>` with `EXPONETDB_PUBLIC_URL` set to that
  exact origin and `/api`, `/auth` and `/oauth` proxied to `serve`, with the
  `Origin` header preserved (plain `http:` is accepted only on a loopback
  host, and Chromium treats `http://localhost` as a secure context, so
  `__Host-` cookies work); or
- skip the dev server and serve the built `dist` through `serve` itself, as
  §6 does today (**[OBSERVED]** the way the Web App is tried by hand and
  tested; no Vite dev server or proxy is configured in `apps/web`).

**[ASSUMPTION]** The proxy variant works with `Origin`, `User-Agent` (a
session is bound to a coarse device label) and cookies passed through
unchanged; Phase 1 verifies it in Chromium and this section records the exact
setup.
