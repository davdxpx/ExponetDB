**[DECIDED]** A developer (human or coding agent) can run the whole system
locally **without any access to REOSA or any production system**.

## 1. What runs locally

| Component | Local form |
|---|---|
| Control Store | PostgreSQL 17 container `exdb-control` |
| Managed databases | disposable PostgreSQL containers: `pg16`, `pg17`, `pg18`, each with pgvector, representing targets `demo/app/staging` and `demo/app/production` plus version-matrix targets |
| `serve`, `worker`, `gateway` | one dev process with all three roles (`exponetdb dev`), hot reload; roles can also be started separately to test isolation |
| Node agent | **fake agent** from `packages/testkit` (implements the protocol, simulates capabilities with configurable latency and faults) or the real Go agent against a PostgreSQL container with the helper in a mock mode |
| OAuth | the ExponetDB authorization server itself; a dev-only seeded owner with a known passkey replacement (TOTP secret printed on seed); loopback redirect for CLI and MCP clients |
| MCP | `http://localhost:<port>/mcp`; the dev server allows `http://localhost` origins; an MCP inspector configuration is provided |
| Object storage | S3-compatible container (for backup engine tests) |

Started by one command (`exponetdb dev up` wrapping a compose file), torn down
by one command; data lives in named volumes that `dev reset` removes.

## 2. Seed data

`exponetdb dev seed` creates:

- product `demo` with environments `staging` (nonprod) and `production` (prod,
  evidence from staging), project `app`, targets on the local containers;
- identities: one owner, one developer bound to nonprod, one viewer; one
  service account; one pre-approved local MCP client;
- a migration stream with ~20 bundles covering every class (additive,
  destructive, non-transactional, rewrite, data migration, security change);
- a legacy-import fixture: a database with a hand-written migration history
  that has gaps, duplicates and post-apply edits (modeled on the REOSA
  findings, without REOSA content);
- findings, health history and statement statistics generated by running a
  synthetic workload for a few minutes.

## 3. Fixtures

| Fixture | Use |
|---|---|
| Migration bundles corpus | lint, checksum, DAG and analysis tests; golden vectors shared by the TypeScript production code (the server and the CLI use the same `packages/migrations/format`) and the Go conformance implementation in `agent/node` (checksums must match across languages) |
| Hostile identifiers | names with quotes, `$$`, Unicode, reserved words, 63-byte names in every object class |
| Large catalog | generator for thousands of tables, indexes and policies (plan-guard budget tests) |
| Supabase-shaped database | a database with `auth`, `storage` and Supabase roles, to test managed-scope filtering and legacy import from Supabase-hosted projects |
| Fault scripts | network partition, agent crash mid-job, Control Store restart, lock contention, statement timeout, disk full simulation (fake agent) |

## 4. Rules

- No environment variable, fixture or script points to a real host. CI fails
  if a fixture contains a non-local hostname other than documentation examples.
- The dev server prints a banner "development mode: not for real databases"
  and refuses to start with `EXPONETDB_PUBLIC_URL` on a non-localhost domain
  unless the dev flag is off.
- Coding agents working in this repository use the local stack and its MCP
  endpoint; they never receive credentials of shared environments.

## 5. What exists since Wave 2

**[DECIDED]** Until `exponetdb dev up` exists, the services the integration
suites need are started by one script. Integration suites never fall back to
an emulation and are never skipped: without their services they fail with a
message that points here.

```sh
eval "$(bun run --silent dev:control-store)"   # starts the containers, exports the variables
bun run test:integration                         # every *.int.test.ts against them
```

| Container | Image (pinned by digest, as in CI) | Variables |
|---|---|---|
| `exdb-control` | `postgres:17.11` on `127.0.0.1:55432` | `EXDB_TEST_PG_URL`: a superuser URL of the disposable server; the suites create the five Control Store roles with the production bootstrap SQL and one fresh database per suite; migrations of parallel suites take turns under an advisory lock, because the roles' connection limits are cluster-wide (production values) |
| `exdb-s3` | `versity/versitygw:v1.8.0` on `127.0.0.1:57070` (S3-compatible, Apache-2.0) | `EXDB_TEST_S3_ENDPOINT`, `EXDB_TEST_S3_ACCESS_KEY`, `EXDB_TEST_S3_SECRET_KEY`: the audit checkpoint export contract |

`bun run verify` runs every CI check of the TypeScript, integration and Go
jobs, the integration suites included. The image job is separate because it
needs a Docker daemon: `bun run smoke:image` builds the image and runs the
role-start smoke test (`tooling/smoke/roles.sh`: bootstrap SQL, migrate,
serve, worker and gateway healthy from one image, graceful shutdown, no
secret in any log), as CI does.

The generated superuser password and S3 secret are written to
`.exdb-dev-superuser` and `.exdb-dev-s3-secret` (mode 0600, git-ignored). The
S3 container keeps its data in memory; it proves the export protocol, not an
off-host store.

## 5a. Managed-target servers (Wave 4)

**[DECIDED]** (Wave 4.) The managed-target suites (`packages/postgres`,
`packages/registry`, `packages/diagnostics` and the server's registry
tests) need PostgreSQL 16, 17 and 18 as managed targets. One script starts
them, TLS only, with a CA generated for the run:

```sh
eval "$(bun run --silent dev:targets)"   # starts the containers, exports EXDB_TEST_TARGETS
```

| Container | Image (pinned by digest, as in CI) | What it is |
|---|---|---|
| `exdb-target-pg16`, `-pg17`, `-pg18` | `pgvector/pgvector:pg16/17/18` (16.15, 17.11, 18.6 with pgvector 0.8 and `pg_trgm`) on `127.0.0.1:55516`, `55517`, `55518` | TLS only: `hostssl … scram-sha-256` and `hostnossl … reject`; the server certificate names `pg.exdb.test` and `localhost`; `max_connections = 200` |
| `exdb-target-plain` | `pgvector/pgvector:pg17` on `127.0.0.1:55599` | without TLS: the plaintext-refusal tests |

`EXDB_TEST_TARGETS` names `targets.json` in the output directory
(`.exdb-dev-targets/`, git-ignored, mode 0600): the servers, the CA, an
unrelated CA, the server certificate and key (for the fault proxy) and the
superuser password, all generated for the run and used for nothing else.
The suites create ExponetDB's roles with the product bootstrap SQL
(`clusterBootstrapStatements`), fresh databases per suite, and copy fixture
databases from templates (`@exponetdb/testkit`: hostile metadata, the
REOSA-shaped synthetic schema, the 2,000-table plan-guard catalog). Without
the variable the suites fail; they are never skipped.

## 6. What exists since Wave 3A

**[OBSERVED]** (Wave 3A, G3A accepted 2026-10-06.) The browser
end-to-end suite needs, besides the database of §5, the built Web App, the
built CLI (`apps/cli/dist`, run with Node as its own process) and Chromium
for the pinned `playwright-core` (an `apps/server` dev dependency):

```sh
node apps/server/node_modules/playwright-core/cli.js install chromium   # once per version
bun run test:e2e        # builds apps/web and apps/cli, then runs apps/server/test/*.e2e.test.ts
```

The suite starts the real `serve` role on `http://localhost:<port>` (a
secure context for WebAuthn and `__Host-` cookies in Chromium), adds a
virtual WebAuthn authenticator through the Chrome DevTools Protocol and
walks the first-owner setup, passkey and password sign-in, re-authentication,
recovery and the request protections, then the Wave 3B flows: the CLI's
loopback sign-in through the consent page, a DCR client approved by an
administrator with an untrusted name and refresh-token reuse, the device
flow, and service-account keys with an API key shown once. Callbacks to
the synthetic `agent.example.test` host are answered inside the browser
(Playwright routing); nothing leaves the machine. It is never skipped;
without Chromium, the built Web App and CLI or the database it fails. `bun run verify` includes it.

To try the Web App by hand against the local database: build it (`bun run
--cwd apps/web build`), run `serve` with `EXPONETDB_PUBLIC_URL=http://localhost:8080`
(plain `http:` is accepted only on a loopback host), and issue the setup
link with `exponetdb bootstrap owner --email owner@example.test` and the
`exdb_serve` login. Only synthetic addresses (`@example.test`) are used in
development and tests.
