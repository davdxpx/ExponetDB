# Golden vectors

Data only. Every file here pins a stored or wire contract that two independent
implementations must reproduce byte for byte:

- the TypeScript production code (`packages/kernel`, `packages/migrations/format`,
  `packages/audit`);
- the Go conformance implementation (`agent/node/internal/canon`,
  `agent/node/internal/conformance`), written from the specification, never from
  the TypeScript code; for the audit chain hash `ac1`, which the node agent
  never computes, the second implementation is the SQL function `audit.ac1`
  that the Control Store's chain guard runs on every insert; for the secret
  envelope `se1` and the policy version `pv1`, the expected values come from
  independent Python derivations (see below).

No implementation lives in `tooling/`. Nothing here is generated by either
implementation.

## How the expected values were derived

- Canonical SQL texts, projections (`applyProjection`, `verifyProjection`,
  `rollbackProjection`), `ls1` hash inputs and plan canonical forms are written
  by hand from the specification.
- JCS expectations come from RFC 8785 (sections 3.2.2, 3.2.3 and Appendix B)
  or are written by hand, then cross-checked against V8's `JSON.stringify` with
  recursively sorted keys (which differs only where JavaScript objects reorder
  integer-like keys, as in `jcs-002`).
- Digests are SHA-256 over the hand-assembled hash inputs, framed exactly as
  N6 states, computed with a standard SHA-256 tool.
- `se1` values were computed by a short Python script with the
  `cryptography` package (AES-256-GCM, HMAC-SHA-256) from the specification
  in `secrets.md` §2.1; keys, data keys and nonces are synthetic SHA-256
  chains of labels, never real key material.
- `pv1` versions were computed by a short Python script (`json` with sorted
  keys over inputs restricted to strings, integers, booleans and null, where
  that equals JCS, and `hashlib`) from the specification in
  `policy-engine.md` §5.1.
- `ac1` hashes were computed by a short Python script written from the
  specification in `audit.md` §4.1 (standard-library `json` with sorted keys
  and `hashlib`), independently of both implementations; the refusal codes
  follow the order the specification lists.

- `fp1` documents have no second introspection implementation: each vector
  carries the SQL of a synthetic fixture, and the document is what the Wave 4
  introspection reads from a fresh database built from it on PostgreSQL 16, 17
  and 18 (`packages/postgres/test/golden.int.test.ts` rebuilds every vector on
  every run). The documents were reviewed by hand against
  `schema-fingerprints.md` §3 and §4. Every entry hash, every fingerprint, the
  entry order and the omission rules, and every expected diff with its
  security relevance, were re-derived by a short Python script (its own RFC
  8785 serializer for this value domain, `hashlib`) written from
  `schema-fingerprints.md` §1, §4 and §6 and `drift-detection.md` §7,
  independently of the TypeScript code; `packages/postgres/test/golden.test.ts`
  reproduces them without a database. The vectors assume the matrix servers'
  superuser `postgres` (owners and ACLs name it).

Anyone can re-derive a digest: build the frames from the `expected` texts
(`executableText` for `up.sql` and `down.sql`, `verifySource` for
`verify.sql`) and hash them with `sha256sum`.

## `fp1` (frozen since G4)

`fp1.json` and `schema-diff.json` are locked like every other file. Before
G4 a defect in the canonical form could still be corrected (listed in the
[G4 gate record](../../exponetdb-docs/14-roadmap/gates/4.md)). G4 was
accepted on 2026-10-07 under the owner's conditional delegation (baseline
`04b2e77`): since then `fp1` is frozen, `fp1-001` to `fp1-018` and
`diff-001` to `diff-007` are append-only, and a semantic correction is
`fp2` through an ADR
([`schema-fingerprints.md` §11](../../exponetdb-docs/03-database-model/schema-fingerprints.md#11-corrections-and-fp2)).

## Rules

- **Append-only since G1.** `c1`, `ls1`, JCS and the plan-hash construction
  are frozen since the owner accepted the Wave 1 gate (G1) on 2026-10-05
  (baseline `b52a6ca`). A vector is never edited or removed; a fix or
  an improvement is a new canonicalizer (`c2`, `ls2`) introduced by an ADR,
  with its own vectors. `LOCK.json` records the hash of every vector, and CI
  fails when a locked vector changes or disappears (`bun run golden:check`).
- **History is checked against a base commit.** `golden:check` sees only the
  current tree: a change that edits a vector, its expected value and its
  `LOCK.json` entry together is consistent there. `bun run golden:history
  <base-ref>` compares the current tree with the base and fails when any
  vector, any top-level file member (`contract`, `specification`, `notes`) or
  any `LOCK.json` entry of the base was changed or removed, when a vector file
  of the base disappeared, or when a new vector has no matching lock entry.
  Comparison is canonical (RFC 8785): reformatting or reordering is not a
  change. A base ref that is missing or unreadable fails closed. There is no
  option to accept a new baseline, rewrite or update an existing entry, or
  skip the check.
- **Frozen Control Store bundles.** The same guard reads
  `packages/control-store/frozen-bundles.json` at the base and refuses a
  changed or removed entry and any byte change (edit, added or removed
  file) of a listed bundle's directory relative to the base commit
  ([`control-database.md` §5](../../exponetdb-docs/02-control-plane/control-database.md#5-the-control-stores-own-migrations)).
  The list lives outside this directory because it pins accepted
  deliverables, not a contract with two implementations.
- **Where the base comes from.** In CI, a pull request compares with
  `github.event.pull_request.base.sha`, a push to `main` with
  `github.event.before` (checkout with full history). `bun run verify`
  compares with `origin/main`. The guard is only as strong as the rule that
  changes reach `main` through pull requests with required CI: branch
  protection on `main` (required pull request, required `ci` checks, no
  force push) is the boundary, and a pull request that edits the guard or the
  workflow itself is a reviewer's concern, not something the guard can
  detect.
- Vector ids are unique per file and never reused.
- Files are byte-exact (`-text` in `.gitattributes`). Biome does not format
  them.
- Synthetic data only: no customer data, no REOSA content, no credentials.
