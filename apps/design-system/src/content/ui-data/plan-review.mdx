# Plan review: frame, checklist, summary and steps

A plan is the statement of a change that has not happened yet. Its review page is where a person decides whether it
should. The page is built from blocks, each of which shows one kind of fact the server computed, in a fixed order, so
that a person who has reviewed one plan knows where to look in the next.

Guidance: [Plan and apply flow](/guidance/plan-and-apply) and [Production cues](/guidance/production-cues).

| Block | Shows | Page |
|---|---|---|
| `PlanFrame` | The reserved production frame and one sentence around the whole review. | this page |
| `PlanChecklist` | "Before it can run": one row per check with its state. | this page |
| `PlanDetailsList` | The technical details: ids, the full plan hash, class, creator, client, times, rules. | this page |
| `PlanSummaryBlock` | Target, tier, kind, class, state, creator, client, times, plan hash and the plan's actions. | this page |
| `PlanStepsBlock` | What will run, in order. | this page |
| `PlanAnalysisBlock`, `PlanEvidenceBlock`, `PolicyDecisionBlock` | The analysis, the evidence and the decision. | [Plan review: analysis, evidence and policy](/ui-data/plan-analysis) |
| `ApprovalsBlock`, `ApplyVerifyIndicators`, `RawPlanTextBlock` | Approvals, the outcome and the text. | [Plan review: approvals, outcome and text](/ui-data/plan-decision) |

The order of the page is fixed and reads top-down (**[DECIDED]** by the owner on 2026-10-21): the page header says what
happens ("Apply 2 migrations to shop/platform/production", "Enroll a node on server tour host"), the plan's state, its
expiry and who created it through which interface, with the actions on its right; then **Before it can run**
(`PlanChecklist`); then **What changes**: the migrations, their analysis and the files the plan runs as data, or for
another kind the stored change in a closed disclosure; then the **Technical details**, closed (`PlanDetailsList`). A
person reads the server's facts before the text the plan carries, because text can be written to mislead.

The blocks below compose the same facts in blocks; the app's plan page uses the checklist and the details list.

## Rules for every block

1. **The blocks decide nothing.** Whether a person may approve or apply is the server's answer. A block shows that
   answer and offers an action only when the answer says it is available.
2. **A value that is missing is "not known".** The server's own `unknown` too. A missing class is never "low", a missing
   decision never "allow", a missing tier never "non-production". The blocks say "not known" in a style that does not
   read as a value.
3. **A name from outside is untrusted.** The creator's name, the client's own name, migration names, relation names and
   rule messages go through the untrusted text components. A client name carries the marker "name not verified".
4. **Hashes are shown in full.** A plan hash, a checksum and a fingerprint are never cut, never translated and are laid out
   left to right with hidden characters shown by code point.
5. **The same hash everywhere.** The page passes one `planHash` to every block that shows or sends it. The actions receive
   exactly the hash that is on screen, in the `PlanBinding`.

## Plan frame

`PlanFrame` takes `production`, which the page computes as `plan.subject.tier !== 'nonprod'`. That fails closed like the
confirmation dialogs: a tier that is missing or unknown is production. With it, the review gets the reserved `production`
ring and one sentence at its head, in the page's words (`notice`): "This plan changes production.", or for a plan without a
tier (a server or a node plan) "This plan has no target tier; it is treated as production."

Production is said **once** (**[DECIDED]** by the owner on 2026-10-21): the tier chip beside the page title, the frame and
the sentence. No block repeats a chip beside its heading; a chip beside every heading made a production page a wall of
equally loud blocks. The typed and plan confirmations keep their own production frame: they are the moment of the decision.

`PlanBlock` is the frame of one block: a `section` named by its heading, in the default border. Use it for a block of your
own. `headingLevel` fits the block to the outline of the page; the default is 2.

## Before it can run

`PlanChecklist` is one card of rows: what stands between the plan and its effect. Each row has an id (`data-check`), a
state, a title, one line and, when there is more to say, content below the line. The page builds the rows; the card
decides nothing.

| State | Icon | Means |
|---|---|---|
| `passed` | check | The condition holds: allowed, no approval needed, approvals given, evidence present, not expired, verified. |
| `waiting` | clock | It holds once something happens: an approval, the apply, the verification. |
| `blocked` | cross | It does not hold: denied, expired, withdrawn, evidence missing, a failed outcome. |
| `unknown` | question mark | The server did not say. |
| `failed` | warning | The read behind the row failed. A failed read is never shown as passed or as empty. |
| `neutral` | dot | It happened without a verdict: applied, before its verification. Applied is never a passed row. |

The plan page's rows are the policy decision (with the rules that did not pass, only when there are any), the approvals
(with the agent note, the decisions so far, whether the person may decide and the self-approval acknowledgement), the
staging evidence of a production migration, the expiry, and once an operation applies the plan its apply and verification
outcomes as two rows (`applyVerifyChecks`) with a link to the operation.

## Technical details

`PlanDetailsList` lists the record of the plan in a closed disclosure at the bottom of the page: the plan id and the full
plan hash, each with a copy button, the kind, the class with its meaning, the ids of the subject, the tier in words, the
statement classes, who created it and through which interface, the client with its own name marked "name not verified",
the exact times, the operation, the requirements, the rules that did not pass, the bound schema fingerprint and the newest
backup. A fact that does not apply to the plan's kind is **left out** (leave its prop out): statement classes, the schema
state and the backup belong to migrations, the client to a plan made through one. "Not known" stays only where a fact
applies and could not be established (`null`).

## Summary

The summary is the head of the review.

- **Target and tier.** The target path in full with the tier chip. For a cluster or a node plan, the cluster or node id.
- **Change, plan class and statement classes.** The class has its meaning in a sentence. The statement classes found by the
  analysis are shown as classification badges; an empty list reads "None found by the analysis", and `null` reads "not known".
- **State.** In words: "Active", "Accepted: an operation applies it", "Expired", "Invalidated: a binding changed", "Denied by the
  policy" or "Withdrawn".
- **Created by and Through.** The creator (person, service account or ExponetDB itself) and the client kind (Web App, REST API,
  MCP (an AI agent), CLI, CI). The client's own name is shown separately with "name not verified".
- **Expiry.** For an active plan, a live countdown ("Expires in 9 min 59 s") with the absolute time; for others, the time as a record.
  The plan is expired from the instant `expiresAt` is reached. The countdown is announced once when the plan expires, not every second.
- **Plan hash.** In full, with a copy button.

### Actions

`renderActions` receives the `PlanBinding` (`planId`, `planHash`) and returns the actions of the plan, such as "Apply to production"
as the trigger of a `PlanConfirmDialog` and "Withdraw plan". They are rendered only while the plan is active, not expired, shown from a
read that is not stale, and has a known hash. Otherwise the summary says why no action is offered. This is not an authorization: the
server checks every request again.

## Steps

`PlanStepsBlock` lists the steps in the order the plan runs them, numbered. For a migration plan these are the migrations in plan
order, then the verification; on an operation they are its steps with their states.

- A step has a label in ExponetDB's words ("Apply migration"), an optional foreign `name` (the bundle's own name), a `reference` (the
  migration id), a `detail` that is a server fact ("Not in a transaction; runs alone") and a `state`.
- States are pending, running, succeeded, failed and skipped, each with its own icon and word. A state this version does not know is
  shown by its name with "(not a known state)".
- `null` steps read "not known". An empty list reads "The server listed no steps for this plan." These are different statements.

## Accessibility

- Each block is a `section` named by its heading. The production sentence is text.
- A checklist row says its state in words to assistive technology and in its line to everyone; the icon is decoration.
- A list of steps is an ordered list. Facts are description lists.
- The countdown is not a live region; only the expiry is announced.

## Copy

- Block titles are nouns: "Summary", "Steps", "Analysis".
- State the consequence in the buttons: "Apply to production", "Withdraw plan". Never "Confirm".
- "Not known" is the word for a missing fact. Do not use "N/A", "none" or a dash for it.
